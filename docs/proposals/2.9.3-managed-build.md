## Problem

`cmsis_action build`, `rebuild` and `clean` run CMSIS Solution's commands and learn the outcome from the task execution the command returns ([cmsisAction.ts:186](../../src/handler/cmsisAction.ts#L186), [cmsisJobTracker.ts](../../src/cmsisJobTracker.ts)). Three things follow from that:

- **The exit code is not trusted.** CMSIS Solution 1.70.1 closed its build task with 0 whatever cbuild returned, so a build that exits 0 is checked: a fresh `cbuild-idx.yml`, then the image times, and when neither decides, a second `cbuild --log` run, stage B of [cmsisBuildDiagnosis.ts](../../src/cmsisBuildDiagnosis.ts). The re-run costs up to 120 s and can itself be replaced: in vscode-cmsis-solution #696 an automatic `cbuild setup` started during the re-run and the result became *unverified*.
- **The output of the original build is lost.** The text the agent sees is the re-run's log (`out/cmsis-developer-assistant/build-diagnostic.log`) or the csolution messages; a successful build has no log at all. In #140 a CMake version recommendation printed by a successful build reached the agent only because the user pasted it.
- **A result belongs to whatever task ended.** The job binds the execution its command returned; a later build or setup of the same task type can replace it, and `stop_build` ends every build-type task of the window ([cmsisAction.ts:192](../../src/handler/cmsisAction.ts#L192)).

## Current state

### PR #713 (draft, head `d2c0b0c`, not merged)

[csolution-api-v3.d.ts](https://github.com/Open-CMSIS-Pack/vscode-cmsis-solution/blob/d2c0b0c/api/csolution-api-v3.d.ts), implemented in [build-operation.ts](https://github.com/Open-CMSIS-Pack/vscode-cmsis-solution/blob/d2c0b0c/src/tasks/build/build-operation.ts) and [v3-api.ts](https://github.com/Open-CMSIS-Pack/vscode-cmsis-solution/blob/d2c0b0c/src/api/v3-api.ts). V3 no longer inherits V2's `build`; `getApi(2)` keeps the task-based one.

| Part | Behaviour read from the code |
|---|---|
| `build(options?)` | synchronous; returns a `BuildOperation` at once; throws without a loaded solution or after `dispose()`. Options `clean`, `rebuild`, `packs`, `updateRte` as in V2, plus `signal: AbortSignal`. The solution path and the active target set are captured at submission |
| `BuildOperation` | `id` (UUID), `result: Promise<BuildResult>` (stable, may be awaited late), `cancel()` (idempotent), `onOutput: Event<BuildOutput>` (live, no replay), `taskExecution?` (once VS Code accepted the task) |
| `BuildResult` | `status: success \| failed \| cancelled \| skipped`, `exitCode?` (cbuild's own, never inferred), `logFile: Uri` |
| Status rules | `success` only for exit 0; `failed` for non-zero or unknown; `cancelled` when cancelled before the start or interrupted (130); `skipped` when an identical request is already queued: no exit code, empty log, and the queued request's outcome is not shared. A compiler or configuration failure resolves; infrastructure and log-write failures reject |
| `BuildOutput` | `{sequence, timestamp, text, stream: 'combined'}`; text as the runner delivers it, ANSI sequences and CRLF included |
| Log | the complete UTF-8 output of the original run in `<tmpdir>/cmsis-build-*/build.log`, kept until the OS cleans the temp directory; no in-memory copy |
| Queue | the existing task runner, Toolbox environment and serialized toolbox queue; the task label carries `[<id>]`, so a managed build is a task of its own |
| Cancellation | before the start: `cancelled` at once. Running: the request alone does not settle the result; a natural success or failure can win the race |
| Dispose | `dispose()` of the API rejects every operation in flight ("interrupted"); a reload of the extension host settles nothing |
| Not in it | structured diagnostics, per-context results, progress phases (queued/running), build history; stdout and stderr are not separated |

The PR also stops V2 tasks from reporting a cancellation before the process ended (the 100 ms timer in `TerminalTaskRunner` is gone) and makes a queued call cancellable. It was read as not changing what a V2 build task reports on exit, so the exit-0 check here stays for 1.72.0 and every host without #713. Measured 2026-11-17 on the PR build `1.72.1-104-070dccf` (CI run 43923995203, isolated VS Code): `cmsis-csolution.build` and `rebuild` now end with cbuild's real exit code (1 for a compile error, 0 on nightly `1.72.1-86`), whether from #713 or from `main` since -86; this touches the exit-0 check, the diagnostic re-run, #128, #135 and #138.

Open review findings of the Copilot reviewer at `d2c0b0c`: the output root is not captured at submission (a queued build after a solution switch can write to the other solution's output directory); a build cancelled during the `--version` probe can report a synthetic 130 as cbuild's exit code; a child that crashes (SIGSEGV) after a cancel request counts as `cancelled`.

### This extension (2.9.0, and 2.9.1 as proposed)

- `acquireSolutionApi` asks for version 2 and checks four methods by name ([solutionApi.ts:164-169](../../src/core/solutionApi.ts#L164-L169)); 2.9.1 moves it to version 3 with per-method detection.
- The job tracker arms a job before the command goes out, binds the task execution, and answers `running` at the call's deadline; `status` waits for it, and a repeated build attaches to the job in flight ([cmsisAction.ts:203](../../src/handler/cmsisAction.ts#L203)).
- The exit-0 check and the diagnostic re-run, behind `build.diagnosticRerun` ([cmsisBuildDiagnosis.ts](../../src/cmsisBuildDiagnosis.ts)); the error lines from [buildFailure.ts](../../src/core/buildFailure.ts).
- A failed job becomes `TASK_FAILED` in the problem journal ([windowProblems.ts](../../src/windowProblems.ts)); a successful one adds nothing.
- `get_build_diagnostics` reads logs inside the workspace only ([buildInfoHandler.ts:198-206](../../src/buildInfoHandler.ts#L198-L206)); the temp-directory `logFile` is outside it.

## Proposed fix

The tool surface stays: no new tool and no new action. `build`, `rebuild` and `clean` go through `build()` when the host offers the managed operation, through the command and the task tracker otherwise. Builds without a `target` are not refused on 1.72.0 under 2.9.1's decision 1 (V3 required for the API seams), so that host keeps 2.9.0 behaviour; the task path also serves a V3 host built before #713.

### Phase 1: detect the managed build (S)

1. `build` exists by name in V2 and V3 with different return types, so 2.9.1's rule "detect by name, never by version" does not decide it. The managed path is taken when `getApi(3)` answered and a probe of the returned object's shape holds: `build` called only for a real request, its result checked for `id`, `result` and `onOutput` before anything else is trusted; any other shape abandons the operation and the call falls back to the command (decision 1).
2. The memoised API object of 2.9.1 is the one that builds; nothing here disposes it.

### Phase 2: the operation behind `cmsis_action` (L)

1. `build`, `rebuild`, `clean`: one `build({clean, rebuild, packs, updateRte})`; subscribe to `onOutput` and attach both handlers to `result` in the same tick; register the operation in the job tracker under its `id` as the job's binding instead of the task execution (`taskExecution`, when it appears, stays as the link to the terminal).
2. The result: `success` with exit 0 is the success, without the image check and without a re-run; `failed` takes the error lines from the log through [buildFailure.ts](../../src/core/buildFailure.ts) (ANSI stripped, CRLF normalised) and the csolution messages as today; `cancelled` as today's cancelled job; a rejection is `failed` with the error text and the hint to `get_recent_problems`.
3. `skipped`: the request was a duplicate of one already queued. A queued request this extension submitted is found in its own registry, so a repeated call attaches there before it reaches `build()`; a `skipped` answer therefore means a user-started or other extension's build, and the call falls back to the task tracker for it (decision 2).
4. The deadline: a call that ends before `result` settles answers `running` with the job id, as now (decision 3: `running`, not the PR's `pending`); `status` waits for the registered operation and never submits another build.
5. `stop_build`: `cancel()` of the managed operation in flight; the reply says cancellation was requested until the result settles, since a natural success can win. Builds the user started from the CMSIS view are still ended through `cmsis-csolution.stopBuild` (decision 4).
6. Lifetime: settled operations stay in the registry for the window's job retention; after a reload or expiry `status` says the operation is unknown. A wait that runs out never cancels the operation and never starts a replacement.
7. The diagnostic re-run is not used on the managed path. On the fallback path it stays as it is, setting included; #135's cap applies there.

### Phase 3: warnings of a successful build (M)

1. A bounded live tail per operation (the last 64 kB) from `onOutput`; the full text read once from `logFile` when the result settles.
2. A warning scan of the settled log: the CMake recommendation of #140 (`CMake <x> or newer is recommended … You are using CMake <y>`) and the other cbuild and csolution `warning` lines, deduplicated, at most 10 in the reply with a count of the rest. The CMake line is classified as a tool-version recommendation with both versions.
3. The `cmsis_action` and `status` replies of a successful build carry the summary; the problem journal gets one `BUILD_WARNING` per distinct line (source `build`, severity `warning`), so `get_recent_problems` shows them. A warning never turns success into failure.

### Phase 4: the log for `get_build_diagnostics` (M)

1. On settlement the log is copied to `<solutionDir>/out/cmsis-developer-assistant/build-<context>.log` (one per target set, overwritten by the next build), ANSI stripped; the temp file is not read again (decision 5).
2. `get_build_diagnostics` without `file` picks that copy as the newest log, for a successful build too; its reply names the operation id and the captured target, not whichever task ended last.

### Phase 5: texts, knowledge and tests (S)

1. `cmsis_action`'s replies name the source ("cbuild exit 0, original log" versus "verified by a re-run"); the agent guide's build topic and the `cmsis_action` description say so in one line each.
2. The knowledge procedures that tell the agent to read the re-run log keep working: the path of the re-run log is unchanged on the fallback path.

## What changes for the agent and the user

```text
A successful build with a tool warning (#140)

today    cmsis_action {action: 'build'} → succeeded, exit 0 after 125 s; the CMake line only in the terminal
new      the same call → succeeded (cbuild exit 0); 1 warning: CMake 4.2.1 or newer is recommended, 3.31.12 in use;
         get_recent_problems lists it; get_build_diagnostics reads the original log

A build that exits 0 without rewriting its image (#696)

today    a diagnostic re-run; a cbuild setup starts meanwhile; result "unverified"
new      cbuild's exit 0 is the answer; nothing is re-run

stop_build during a long build

today    every build-type task of the window ends
new      this extension's operation is cancelled; "cancellation requested" until cbuild exits
```

## Gaps on the CMSIS Solution side

- **B1 Not merged.** Draft, three open review findings (above); the shape may change before the merge.
- **B2 Same method name, two contracts.** V3 `build` returns an operation, V2 `build` a task-based result; a capability flag or a distinct name (`startBuild`) would make detection safe.
- **B3 No phase.** Queued and running are not told apart; the reply can only say `running`.
- **B4 `skipped` does not name the request it duplicates;** an operation id of the queued request would let this extension attach to it.
- **B5 Log in the temp directory,** removed at the OS's discretion; an option for the log folder, or the solution's `out/`, would spare the copy.
- **B6 One stream, no structure.** Warnings and errors are read from text; structured diagnostics per context are out of the PR's scope.
- **B8 Identical concurrent requests break (measured 2026-11-17 on `1.72.1-104-070dccf`).** Two or three identical `build()` calls: the first resolves `failed` with no exit code and an empty log although its build succeeded; the last resolves with the real result but carries the first one's task execution; with three, the middle one never settles until `cancel()`. `skipped` never came back. Different requests (build, then rebuild) queue and both succeed. Decision 2 relies on this extension never sending a duplicate; file with B2–B5.
- **B9 `getPacks` with scope `used` or `missing`** throws "a valid solution must be loaded" on a loaded, converted solution (same as on nightly 1.72.1-112; 2.9.1's concern).
- **B7 No events for builds the user starts.** A managed operation exists only for API callers; the CMSIS view's builds still need the task tracker.

## Decisions for you

- [x] **1. Detection.** Decided 2026-11-17 as recommended: `getApi(3)` plus a shape check of the returned operation, fallback to the command. 2.9.1 requires V3 for its seams; this one keeps the fallback because a build is the one action every host must still run.
  - Alternative: wait for a capability flag or a distinct method name (B2) before using it.
- [x] **2. `skipped`.** Decided 2026-11-17 as recommended: attach in this extension's registry first; a `skipped` answer falls back to the task tracker.
  - Alternative: answer `skipped` to the agent as "a build is already queued" and let it call `status`.
- [x] **3. Status word.** Decided 2026-11-17 as recommended: keep `running` (the tool contract and the snapshots use it); the PR's `pending` is not adopted.
- [x] **4. `stop_build`.** Decided 2026-11-17 as recommended: cancel this extension's operation, and `cmsis-csolution.stopBuild` only when no managed operation is in flight.
  - Alternative: always both, as today.
- [x] **5. The log.** Decided 2026-11-17 as recommended: copy into `out/cmsis-developer-assistant/` on settlement.
  - Alternative: let `get_build_diagnostics` read the registered `logFile` by operation id, outside the workspace rule.
- [x] **6. Filing upstream.** Decided 2026-11-17 as recommended: B2, B3, B4 and B5 as review comments on #713 now; B6 and B7 as issues after the merge. Not filed yet.

## Tests and acceptance

- **Unit:** a scripted V3 object whose `build` returns an operation that settles `success`, `failed` (error lines from the log), `cancelled`, `skipped`, and rejects; output events before and after the deadline; a V2-shaped `build` under `getApi(3)` falls back; the warning scan with the CMake line, duplicates and more than ten warnings; the log copy with ANSI and CRLF.
- **Scenarios:** `dap-scenarios` of `cmsis_action build`, `status` and `stop_build` on a managed host and on 1.72.0.
- **Surface:** the `cmsis_action` description and the build replies change; `surface.snapshot.json` and `dap-scenarios.snapshot.json` updated in the same commit.
- **Live** with a nightly that contains #713: #140's reproducer (SEGGER-RTT, `CYT4BF8CDS@file-io`, CMake 3.31.12) shows the warning in `cmsis_action`, `get_recent_problems` and `get_build_diagnostics` without a re-run; #696's long Zephyr build with `autoConvertOnFileChange` on reports cbuild's own result; `stop_build` during a build; the same calls on 1.72.0.

## Out of scope and follow-ups

- Load, erase, run and debug: they stay task-based until CMSIS Solution offers operations for them.
- Raw terminal capture of other tasks (#69).
- Structured diagnostics (B6): the error lines stay a text scan.
