## Problem

`cmsis_action build`, `rebuild` and `clean` run CMSIS Solution's commands and learn the outcome from the task execution the command returns ([cmsisAction.ts:186](../../src/handler/cmsisAction.ts#L186), [cmsisJobTracker.ts](../../src/cmsisJobTracker.ts)). Three things follow from that:

- **The exit code is not trusted.** CMSIS Solution 1.70.1 closed its build task with 0 whatever cbuild returned, so a build that exits 0 is checked: a fresh `cbuild-idx.yml`, then the image times, and when neither decides, a second `cbuild --log` run, stage B of [cmsisBuildDiagnosis.ts](../../src/cmsisBuildDiagnosis.ts). The re-run costs up to 120 s and can itself be replaced: in vscode-cmsis-solution #696 an automatic `cbuild setup` started during the re-run and the result became *unverified*. The analysis there names the re-run as the likely cause: a second incremental build outside CMSIS Solution's queue, ended by this extension when another build-type task starts.
- **The output of the original build is lost.** The text the agent sees is the re-run's log (`out/cmsis-developer-assistant/build-diagnostic.log`) or the csolution messages; a successful build has no log at all. In #140 a CMake version recommendation printed by a successful build reached the agent only because the user pasted it.
- **A result belongs to whatever task ended.** The job binds the execution its command returned; a later build or setup of the same task type can replace it, and `stop_build` ends every build-type task of the window ([cmsisAction.ts:192](../../src/handler/cmsisAction.ts#L192)).

| Part | Behaviour read from the code |
|---|---|
| `build(options?)` | unchanged from V2: resolves to the VS Code `TaskExecution` of the build task. No operation object, no id, no `signal` |
| `getBuildResult(execution)` | the `BuildResult` of that execution; the same promise on every call. It settles when the runner has finished, not when the task ends. The handle may come from any entry point (the commands of the CMSIS view, V2 or V3 `build`, a setup task, a CMSIS build task of `tasks.json`), from VS Code's task events, after the build has ended, and through another V3 object. Rejects "No captured build result is available for this task execution" for a handle that is no CMSIS build task or was never captured |
| `getBuildResult()` | the latest completed build of the loaded solution and its active target set, failures included, or `undefined`; does not wait for a running build. Clean and setup tasks are not recorded there (their handle still works) |
| `BuildResult` | `{exitCode?: number, output: string}`; no status word |
| `exitCode` | the runner's code: cbuild's, or a negative toolbox error. `undefined` when the toolbox queue skipped the call as redundant, when a cancelled build still ended with 0, when the runner failed to start (the error is in `output`), and when the task ended without a capture (`output` is then `''`). A cancelled build that ends non-zero keeps its code. Only 0 means success |
| `output` | everything written to the task's terminal, in order, as one string: ANSI sequences, CRLF, the closing lines ("Build cancelled by user"), the warnings of a successful build; verbosity as set for builds |
| Retention | memory only: per execution in a `WeakMap`, alive while someone holds the handle or the promise, and one latest result per solution and target set until it is replaced or the extension ends. No size limit, no file; a reload of the extension host loses all of it |
| Context | the solution and the target set are bound when the task starts, before the toolbox queue, so a later switch changes neither what is built nor where the result is recorded |
| Cancellation | none in the API: `execution.terminate()` or `cmsis-csolution.stopBuild` as before. The terminal still closes with 130 after 100 ms; the result waits for the runner and carries its last output |
| Queue | the existing task runner and toolbox queue; no new task, label or dependency |
| Not in it | live output, a status or a reason, results per context, structured diagnostics, a log file, an operation id, a history beyond the latest build |

**The build task's own exit code.** Independent of #720, `main` closes the build task with the runner's exit code since `2dc5a9b` (vscode-cmsis-solution #704, merged 2026-11-13); before that it was always 0. Nightly `1.72.1-112`, #713's branch and #720 contain that commit; 1.72.0 and nightly `1.72.1-86` do not. This is what the measurement of 2026-11-17 on the #713 build `1.72.1-104-070dccf` saw (`cmsis-csolution.build` ending with 1 for a compile error). A V3 host with #704 and without #720 cannot be told by a method name from an earlier V3 nightly without it (`a9c1e69` predates `2dc5a9b`), so the exit-0 check stays for every host without `getBuildResult`; it touches #128, #135 and #138.

**What #713 had and #720 does not.** The operation object (`id`, `result`, `cancel()`, `onOutput`, `taskExecution`), the status words `success | failed | cancelled | skipped`, the `AbortSignal` option, the log file in the temp directory and the task label with the operation id. The three review findings recorded here on 2026-11-17 concerned that code and are dropped. ### This extension (2.9.0, and 2.9.1 as proposed)

- `acquireSolutionApi` asks for version 2 and checks four methods by name ([solutionApi.ts:164-169](../../src/core/solutionApi.ts#L164-L169)); 2.9.1 moves it to version 3 with per-method detection.
- The job tracker arms a job before the command goes out, binds the task execution the command returns, and answers `running` at the call's deadline; `status` waits for it, and a repeated build attaches to the job in flight ([cmsisAction.ts:203](../../src/handler/cmsisAction.ts#L203)). ## Proposed fix

The tool surface stays: no new tool and no new action. On a host whose V3 object has `getBuildResult`, `build`, `rebuild` and `clean` start through V3 `build(options)` instead of the `cmsis-csolution.*` commands (decision 1: no command where the API offers the call), the job tracker binds the execution the call resolves to, and the result is asked from the API for that execution. On every other host (1.72.0, a V3 nightly before #720) the path of 2.9.0 runs unchanged, commands included. Builds without a `target` are not refused on 1.72.0 under 2.9.1's decision 1.

### Phase 1: detect `getBuildResult` (S)

1. By name on the V3 object, 2.9.1's rule: `getBuildResult` and `build` both present select the API path. The shape probe of the #713 design is not needed: `build` is unchanged and the new method has a name of its own (decision 1).
2. A `getBuildResult(execution)` that rejects (an unknown handle, a capture that was not active) sends that one build to the 2.9.0 check; it does not switch the path off for the window.

### Phase 2: the result behind `cmsis_action` (M)

1. The job starts its build with `build({clean, rebuild, packs})` and binds the `TaskExecution` the call resolves to; a rejection is the failed start, with its text. `build()` is not the command (read at `0dfe856`, [build-command.ts](https://github.com/Open-CMSIS-Pack/vscode-cmsis-solution/blob/0dfe856/src/tasks/build/build-command.ts) against [v2-api.ts](https://github.com/Open-CMSIS-Pack/vscode-cmsis-solution/blob/0dfe856/src/api/v2-api.ts)), so this extension does what the command did before the task: it waits for a running setup task and for a build in flight (the tracker's holding and attaching, #138), saves modified editors when `task.saveBeforeRun` is `always` and otherwise builds what is on disk and says so, never with the command's modal question; runs 2.9.1's `convertSolution` check when the YAML changed; and passes `packs` from CMSIS Solution's setting for missing packs, which the command reads and the API defaults to off. The output verbosity is `normal` on this path whatever the user's setting says (B13).
2. When the job binds its execution it asks `getBuildResult(execution)` once and keeps the promise. The job settles from that promise, not from the task's end event: the event can arrive 100 ms after a stop request while cbuild still runs. The end event starts a fence instead; a result that has not settled 10 s after it sends the job to the 2.9.0 check, and the reply says so.
3. `exitCode` 0 is the success, without the image check and without a re-run. Non-zero is `failed`, with the error lines taken from `output` through [buildFailure.ts](../../src/core/buildFailure.ts) (ANSI stripped, CRLF normalised) and the csolution messages as today.
4. `exitCode` undefined is never a success (decision 2). It is `cancelled` when this extension asked for the stop or the task's process ended with 130, as today. Otherwise the build was skipped as a duplicate or its code is not available: the call attaches to a build-type task of the window that is still in flight, as a repeated build does today, and without one it answers `unverified` with the end of `output` and the advice to build again. Nothing is re-run.
5. The deadline: a call that ends before the result settles answers `running` with the job id, as now (decision 3); `status` waits for the job's promise and never starts a build.
6. `stop_build` terminates the bound execution of this extension's own build; `cmsis-csolution.stopBuild` goes out only when no build of ours is in flight (decision 4, with `terminate()` where #713 had `cancel()`). The reply says "stop requested" until the result settles, and a stopped build keeps its last output.
7. Lifetime: once the result is taken and the log written (phase 4), the job drops the handle and the promise, so CMSIS Solution can free the text; the tracker keeps its own summary for the job retention. After a reload `status` says the job is unknown.
8. The diagnostic re-run is not used on this path. On the 2.9.0 path it stays as it is, setting included; #135's cap applies there.

### Phase 3: warnings of a successful build (M)

1. `output` is read once, when the result settles. There is no live tail: #720 has no output events, so a running build shows nothing until it ends.
2. A warning scan of the cleaned text: the CMake recommendation of #140 (`CMake <x> or newer is recommended … You are using CMake <y>`) and the other cbuild and csolution `warning` lines, deduplicated, at most 10 in the reply with a count of the rest. The CMake line is classified as a tool-version recommendation with both versions.
3. The `cmsis_action` and `status` replies of a successful build carry the summary; the problem journal gets one `BUILD_WARNING` per distinct line (source `build`, severity `warning`), so `get_recent_problems` shows them. A warning never turns success into failure.

### Phase 4: the log for `get_build_diagnostics` (S)

1. On settlement the cleaned `output` is written whole to `<solutionDir>/out/cmsis-developer-assistant/build-<target set>.log`, one file per target set, overwritten by the next build (decision 5). It survives a reload, which the API's copy does not.
2. `get_build_diagnostics` without `file` picks that file as the newest log, for a successful build too; its reply names the job and the target set the build was started for, not whichever task ended last.
3. Only a build or a rebuild writes the log, feeds the warning scan and adds journal entries, as #720's own latest result leaves clean and setup out. A clean of ours and a `cbuild setup` task are asked for their exit code and nothing else, so neither overwrites the log of the build before it.
4. A build this extension did not start (the CMSIS view, a task of `tasks.json`) gets the same treatment: the tracker sees its execution in the task events, asks for its result, writes the log and scans the warnings (decision 7). `getBuildResult()` without a handle covers a build that ended before this extension was listening: `get_build_diagnostics` asks it when the active target set has no log from this session, and labels the answer "latest build recorded by CMSIS Solution".

### Phase 5: texts, knowledge and tests (S)

1. `cmsis_action`'s replies name the source ("cbuild exit 0, original output" versus "verified by a re-run"); the agent guide's build topic and the `cmsis_action` description say so in one line each.
2. The knowledge procedures that tell the agent to read the re-run log keep working: the path of the re-run log is unchanged on the 2.9.0 path.

## What changes for the agent and the user

```text
A successful build with a tool warning (#140)

today    cmsis_action {action: 'build'} → succeeded, exit 0 after 125 s; the CMake line only in the terminal
new      the same call → succeeded (cbuild exit 0); 1 warning: CMake 4.2.1 or newer is recommended, 3.31.12 in use;
         get_recent_problems lists it; get_build_diagnostics reads the original output

A build that exits 0 without rewriting its image (#696)

today    a diagnostic re-run; a cbuild setup starts meanwhile; result "unverified"
new      cbuild's exit 0 is the answer; nothing is re-run

stop_build during a long build

today    every build-type task of the window ends; the reply follows the task's end event
new      this extension's build is terminated; "stop requested" until cbuild has ended, its last output kept
```

## Gaps on the CMSIS Solution side

The letters of 2026-11-17 are kept, since the notes refer to them.

- **B1 Not merged.** #720 is open with a review requested from @edriouk; CI is green. The nightly of 2026-11-18 (`f4b6d56`, the PR's merge base) does not contain it. The shape may change before the merge.
- **B2 Same method name, two contracts.** Gone with #720: `build` is unchanged, the new method has its own name.
- **B3 No phase, and now no status.** Queued and running are still not told apart, and a skipped build, a cancelled one that ended 0, a runner that failed to start and a task without a capture all read `exitCode: undefined`. A `status` or `reason` field would spare the guessing of phase 2 step 4.
- **B4 A skipped build does not name the one it duplicates.** There is no id any more; the build in flight is found among the window's task executions.
- **B5 The text lives in memory only.** #713 wrote a file in the temp directory; #720 keeps a string of any size, per handle for as long as the handle is reachable and per target set until the next build. A size limit, or a file, would bound it; a reload of the extension host loses every result.
- **B6 One stream, no structure.** Warnings and errors are read from text, with terminal formatting in it.
- **B7 No events for builds the user starts.** Largely gone with #720: every build of the provider is captured and can be read by its handle or as the latest.
- **B8 Identical concurrent requests.** Measured 2026-11-17 on the #713 build only (the first of two identical `build()` calls failed with an empty log, the last carried the first one's task, a middle one never settled); that code is not in #720. Read from #720: the toolbox queue still drops a redundant queued call and now reports it, so the second build should resolve with `exitCode` undefined and little or no output. A handle is matched to its capture through a first-in-first-out list per task definition, so two builds with the same definition are the case to probe. To measure on a #720 build.
- **B9 `getPacks` with scope `used` or `missing`** throws "a valid solution must be loaded" on a loaded, converted solution (2.9.1's V12); not touched by #720.
- **B10 No live output.** #713 had `onOutput`; with #720 nothing is known of a long build until it ends.
- **B11 The latest result is coarse.** One per solution and target set, not per context; clean and setup are left out; a task that ended without a capture records an empty result as the latest.
- **B12 The capture is keyed on the handle object.** This design assumes that the `TaskExecution` this extension gets from `build()` and from the task events is the object the provider recorded. The README of #720 says so; to confirm live before phase 2.
- **B13 `build()` is less than the command.** The API call starts the task with `clean`, `rebuild`, `packs` and `updateRte` only: it does not save modified files, stop a running setup task, wait for a build in flight or refresh a changed solution, and it ignores the user's build settings (output verbosity; missing packs are downloaded by default through the command, not through the API). Options for these, or a call that shares the command's preparation, would let callers drop their own copy of it.

## Decisions for you

- **Surface:** the `cmsis_action` description and the build replies change; `surface.snapshot.json` and `dap-scenarios.snapshot.json` updated in the same commit.
- **Live** with a CMSIS Solution build that contains #720: first that the handle from `build()` is accepted by `getBuildResult` (B12) and what two identical builds answer (B8); then #140's reproducer (SEGGER-RTT, `CYT4BF8CDS@file-io`, CMake 3.31.12) shows the warning in `cmsis_action`, `get_recent_problems` and `get_build_diagnostics` without a re-run; #696's long Zephyr build with `autoConvertOnFileChange` on reports cbuild's own result; `stop_build` during a build; a build started from the CMSIS view; the same calls on 1.72.0.
