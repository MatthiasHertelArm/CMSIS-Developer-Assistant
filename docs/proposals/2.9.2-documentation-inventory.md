## Goals

1. **One inventory.** The documents of a target are one list for the user (the CMSIS view) and the agent (`list_target_docs` and the other four tools). What the user adds, imports or downloads in the view is what the agent lists and searches; what the agent fetches is what the user sees.
2. **Technical: the logistics live in CMSIS Solution, the indexing here.** Logistics means which documents belong to a target (pack books, the Arm catalogue, the user's additions), where their files are (download, import, copy, removal, folder layout), their availability state, and the user's actions on them. This extension keeps extraction, the page store, the BM25 index, search, the SVD join and the citations. In the end state `fetch_doc` downloads through CMSIS Solution, this extension's user folder, import wizard and download trees are gone, and the Arm catalogue is read from the inventory instead of being shipped twice.
3. **UX: the user sees what documentation is available, adds custom documents easily, and is warned when the agent needs a document that is not local.** For every document of the target the view says whether it is a pack file, a local copy, a web link that one click downloads, or something only the user can get, for example behind a vendor login. A document the agent asked for and could not get carries a warning indicator with the action that resolves it: *Download*, or *open the vendor page, download, Import*. Adding a datasheet is one action on the device or board node, or on the active target from the palette, without a wizard.

## Problem

Since CMSIS Solution `main` of 22–30 October there are two document managers for the same target, and neither sees the other:

- **What the user adds, the agent does not see.** *Add Document* in the CMSIS view copies a datasheet to `~/.cmsis/docs/<Vendor>/<Name>/…` and records it in `~/.cmsis/docs.yml`. `list_target_docs` reads the packs, `~/.cmsis-pack-docs/user`, the workspace folders and its own store ([targetDocs.ts:17-31](../../src/core/packDocs/targetDocs.ts#L17-L31)); the new file is not listed, so the agent cannot search it.
- **What the user downloaded, the agent downloads again.** *Download Document* fetches an Arm manual to `~/.cmsis/docs/<id>-<version>/`; `fetch_doc` fetches the same PDF into `globalStorage/packdocs/arm/<id>-<version>/` ([packDocsHost.ts:159](../../src/packDocsHost.ts#L159)), several megabytes twice, and the CMSIS view does not show the agent's copy.
- **The agent's needs are invisible to the user.** When `fetch_doc` fails on a login wall, a 403 or an HTML page where a PDF was expected ([webFetch.ts](../../src/core/packDocs/webFetch.ts)), the agent says so in the chat and nowhere else. The view shows the same document as a plain web link; the user does not learn which file to download by hand, nor where to put it so that the agent finds it.
- **Custom documents are work.** This extension's *Import Document for Current Target* asks for the attribution (pack, vendor, device glob, board glob, core, all), a title, a category and an edition, and writes `docs.json` ([userDocs.ts:17-36](../../src/core/packDocs/userDocs.ts#L17-L36)); CMSIS Solution's *Add Document* asks for a file and attributes it to the node. Two ways, two folders, two vocabularies.
- **Two Arm catalogues.** CMSIS Solution's `dist/arm-docs.json` is byte-for-byte this extension's `src/core/packDocs/armDocs.json`, but its selection (`ArmDocs.getDockIDs`, [arm-docs.ts](https://github.com/Open-CMSIS-Pack/vscode-cmsis-solution/blob/a9c1e69/src/doc-manager/arm-docs.ts)) matches `cores` and `archs` only, so the CMSIS view never lists the ADI, CoreSight and Ethos-U documents that `list_target_docs` lists; #648 asks for the rules.

## Proposed fix

### Stages by what CMSIS Solution offers

The release is planned along the availability of the other side. Each stage is detected at run time, never by a version number, and each stage includes the ones before it.

| Stage | CMSIS Solution offers | This extension does | State |
|---|---|---|---|
| 0 | 1.72.0: no inventory, no V3 | 2.8.0 behaviour (pdsc walk, Arm catalogue, user folder, own store); the target from the cbuild-run file, not from the V3 getters | the fallback, kept: the documentation tools are not refused under 2.9.1's decision 1 |
| 1 | the document manager (`~/.cmsis/docs.yml`, the view's commands) and V3 as on `main` today: the target getters, no document method | reads the inventory as a source, selects by the V3 names, uses the local copies, shows the availability state; keeps its own downloader for what the inventory lacks | nightly today; the work of phases 1–3 |
| 2 | stage 1 plus G1a: `docs.yml` watched, the outline redrawn on an external change | writes `requested` and `error` with the reason into the inventory under its own lock, so the warning of goal 3 shows at once; still downloads itself | small upstream change; the interim of Decision 1 |
| 3 | stage 2 plus G1b: the document methods in V3 (sketch below), `requested` and the reason as inventory state (G10), the failure classes (G8) | hands the logistics over: downloads, requests, imports and the migration through the API; retires its download trees, the user folder and the wizard | the release target; phase 4 |

Sketch of the V3 document methods to request (G1b), in the style of [csolution-api-v3.d.ts](https://github.com/Open-CMSIS-Pack/vscode-cmsis-solution/blob/a9c1e69/api/csolution-api-v3.d.ts):

```typescript
/** A parent of the inventory: a device (Vendor::Name) or a board (Vendor::Name[:Revision]). */
type DocParent = { device: string } | { board: string } | { common: 'arm-docs' };
interface DocumentInfo {
    name: string;                    // URL or path: the identity, as in docs.yml
    title: string; category?: string;
    location: 'pack' | 'web' | 'link' | 'local' | 'user';
    path?: string;                   // the local copy
    requested?: { by: 'agent' | 'user'; at: string; reason?: string };
    error?: { kind: 'login-required' | 'not-pdf' | 'http' | 'network' | 'missing-file'; detail?: string; url?: string };
}
getDocuments(parent: DocParent): Promise<DocumentInfo[]>;
addDocument(parent: DocParent, source: string, meta?: { title?: string; category?: string }): Promise<DocumentInfo>;
downloadDocument(parent: DocParent, name: string, options?: { timeoutMs?: number; maxBytes?: number;
    onProgress?: (bytes: number, total?: number) => void }): Promise<DocumentInfo>;   // rejects with error.kind
importDocument(parent: DocParent, name: string, localPath: string): Promise<DocumentInfo>;
removeDocument(parent: DocParent, name: string): Promise<boolean>;
requestDocument(parent: DocParent, name: string, request: { by: 'agent'; reason: string }): Promise<void>;
readonly onDidChangeDocuments: Event<DocParent>;
```

### The end state (stage 3)

| | CMSIS Solution | This extension |
|---|---|---|
| Which documents a target has | the inventory: pack books, the Arm catalogue, the user's additions | reads the inventory; the pdsc walk and the catalogue rules only as the fallback for stage 0 and for an inventory not yet filled |
| Where the files are | `~/.cmsis/docs/`: download, import, copy, removal | none of its own; the legacy user folder read until migrated |
| Availability state | `path`, `error` with a reason, `requested` | shown in `list_target_docs`, used to choose between index and request |
| The user's actions | Add, Download, Import, Remove, Open, in the view and the palette | none; the Pack Docs panel shows the state and links to the view |
| The agent's requests | recorded in the inventory, shown as a warning with the resolving action | `fetch_doc` asks CMSIS Solution to download, or records the request when only the user can |
| Text, pages, index, search, dossiers, citations | — | the page store, keyed by this extension's ids, never beside the copies |

The flow of an agent request in the end state:

1. `fetch_doc {doc}`: the inventory has a copy → index it. No copy, downloadable → `downloadDocument` (the job waits as today, up to 10 minutes) → index. Not downloadable, or the download fails → `requestDocument` with the reason; the view shows the warning with the action; the tool reply says the same and names the user's action.
2. The user resolves it: *Download* for a plain web link, or *open the vendor page, log in, download, Import* for a protected one. `path` is set, `requested` cleared, `onDidChangeDocuments` fires, the outline redraws.
3. The next `fetch_doc` or `search_target_docs` indexes the copy.

### Phase 1: the inventory as a source (M, stage 1)

1. **`src/core/packDocs/inventory.ts`** (no `vscode`): read `~/.cmsis/docs.yml` with `js-yaml` (users may edit the file; the generated-file subset parser is not for it), per call, no watcher. A parse error skips the source with one note in the listing.
2. **Select by the V3 names.** The device and board of the resolved target come from `getDeviceName()` and `getBoardName()` of the 2.9.1 seam, which read the loaded solution as the inventory's `updateDocs()` does, so the keys match by construction; the processor suffix is dropped as `de60c12` does. Without V3 (stage 0, or a target given by argument) the names come from the cbuild-run file as today and are normalised the same way. The `arm-docs` commons are selected by the core, from the cbuild-run file or the DFP as today.
3. **Map** `IDocRef` to `DocRef`:

   | inventory | `DocRef` |
   |---|---|
   | `name` URL | `url`, id `arm/<id>-<version>` when `armDocRef` recognises it, else `web/<host>/<hash>` |
   | `name` path under the pack | `path`, scope and id as the pdsc walk gives them |
   | `path` (the copy) | `path` for extraction; `cached: true` for a W entry |
   | `title`, `category` | the same; `category` mapped to `BookCategory` |
   | `mode: user` | scope `user`, source `user` |
   | `error`, `requested` | the availability state in the listing |
   | `id`, `version`, `format` | `arm`, `format` |

   Ids stay this extension's, derived from `name`, so tool arguments, the page store and the snapshots do not change for documents that were listed before.
4. **Merge** in `resolveTarget`: inventory entries first, then the pdsc walk, the Arm catalogue, the user folder and the workspace folders, de-duplicated by URL, Arm id and file path. The pdsc walk and the Arm catalogue stay as the fallback: the inventory fills only after a conversion (G6), and stage 0 has none.

### Phase 2: local copies and the availability state (S, stage 1; the request signal at stage 2)

1. A W entry with `path` is extracted from that copy; `fetch_doc` for it answers "downloaded by CMSIS Solution" and indexes without a download.
2. Sidecars stay in `globalStorage/packdocs/` keyed by id, never beside the copy, because *Remove Document* deletes the managed directory. A copy that disappears is listed as "removed in the CMSIS view", not as an error.
3. `list_target_docs` shows the state of every document in the words of goal 3: pack file, local copy, web link (one call or one click downloads it), needs the user (login or manual download, with the URL), download failed (with the reason when the inventory has one), removed. For a document the agent cannot get, the reply names the user's action: *Download Document* in the CMSIS view, or *open the vendor page, download, Import Document*.
4. **At stage 2** `fetch_doc` records `requested` and `error` with the reason in the inventory (load, modify, save under a lock file beside `docs.yml`; only on an existing entry; never touching other fields), so the view's warning appears at once. Detected by the presence of G1a, never assumed.
5. Until stage 3, `fetch_doc` keeps its downloader and store for what the inventory does not hold; writing into `~/.cmsis/docs/` without an inventory entry would show the file in the folder but not in the view.
6. The panel's *delete downloaded PDFs* keeps deleting this extension's trees only.

### Phase 3: texts, commands, knowledge (S, stage 1)

1. *Import Document for Current Target* and *Open User Documents Folder* are marked deprecated in the user guide and point to *Add Document* in the CMSIS view; the legacy folder stays a read-only source until phase 4 migrates it. New imports go through the CMSIS view.
2. The Pack Docs panel's Documents tab shows the inventory state and links to the CMSIS view's actions; it no longer offers its own fetch for a document the inventory lists.
3. Tool descriptions unchanged or shorter (tool-list budget 33 200 B). Texts: [packDocs.md](../architecture/packDocs.md), the user guide (commands table, "Documents the packs do not ship", settings row), README line 193, `debug_instructions.md` where it names the user folder. Knowledge base: `cmsis-pack-docs/SKILL.md` lines 26–36 and 112 and `add-board-layer/SKILL.md` name the import command and the folder; rewrite for the CMSIS view, rebuild, pin a new `core-2026.11.x`.

### Phase 4: the logistics hand-over (L, stage 3)

1. **Downloads through CMSIS Solution.** `fetch_doc` calls `downloadDocument(parent, name, {timeoutMs, maxBytes, onProgress})`; a URL the inventory does not know is added first with `addDocument(parent, url, {title})`. This extension's `arm/` and `web/` download trees are retired; existing downloads are imported once or re-downloaded on demand.
2. **The request signal.** `requestDocument(parent, name, {by: 'agent', reason})` replaces the stage 2 write; the view shows the warning indicator on the document and on its device or board node; `path` clears it.
3. **Needs the user.** CMSIS Solution's downloader classifies a failure: HTTP 401 or 403, an HTML body where a PDF was expected, a redirect to a login page → `login-required` with the URL; a timeout or a 5xx → `http` or `network` with the status; the view's warning says what to do and offers *Import* for the file the user downloaded by hand. This extension has the PDF-or-HTML test in `webFetch.ts`; contribute it (G8).
4. **Custom documents in one action.** *Add Document* on a device or board node and from the palette for the active target exist; ask for drag-and-drop onto the node and for a default title from the file name (G11), and for the attributions this extension's folder scheme had: core, pack or vendor, all targets, custom boards (G2). Then the legacy folder is migrated by a one-time command into `~/.cmsis/docs/` with entries through `addDocument` (Decision 3).
5. **The Arm catalogue** is read from the inventory's commons once G4 gives CMSIS Solution the same selection rules; `armDocs.json` leaves this extension then.

### The CMSIS view in the end state

| State | Indicator | Action on the node |
|---|---|---|
| Pack file present | P | Open |
| Web link, not local | W | Download |
| Local copy of a web link | L | Open |
| Hyperlink (HTML page) | H | Open in the browser |
| User document | U | Open, Remove |
| Requested by the agent, downloadable, not local | warning + W, "requested by the agent" | Download (one click) |
| Requested by the agent, needs the user | warning, "login required at `<host>`" | Open the vendor page; Import the downloaded file |
| Download failed | warning + reason | Retry, Import |
| Copy removed from disk | warning, "file not found" (exists today) | Import, Download |

The device or board node carries the warning of its documents, so a collapsed tree still shows that the agent waits for something.

## Gaps on the CMSIS Solution side

To file on Open-CMSIS-Pack/vscode-cmsis-solution, each on the owner's go; G4 and G8 are contributions. G1a, G1b and G10 are the stage gates.

- **G1a Redraw on external changes (stage 2):** watch `~/.cmsis/docs.yml` and redraw the outline, so that another writer is seen at once. Small.
- **G1b Document methods in API V3 (stage 3):** the sketch above: `getDocuments`, `addDocument`, `downloadDocument` with a budget, progress and a typed failure, `importDocument`, `removeDocument`, `requestDocument`, `onDidChangeDocuments` (`DocManager.onDidChange` exists internally). Today's commands take a `COutlineItem` or open a dialog.
- **G2 Attribution beyond one device or board:** core, pack or vendor, all targets, and `custom::<name>` boards as #594 proposes (not in the code).
- **G3 Project-level documents:** #594 names `./docs/custom/<board>`; the code has only the home inventory. The workspace folders stay this extension's either way.
- **G4 Arm catalogue selection** ignores `all` and `npus`: contribute this extension's rules (ADI and CoreSight for every Cortex-M target; NPU from the subsystem name through `knownNpus`, as `pdscBooks.collectNpus` and `armDocs.knownNpuOf` do) and the version policy (`latest` resolved at download, `resolvedVersion` kept).
- **G5 Format:** a `version:` field and a `schemas/docs.md` like `tools-environment.md`; the new fields `requested` and the reason in `error`.
- **G6 Inventory only after a conversion:** a freshly opened solution lists nothing until a refresh or build.
- **G7 Downloads:** 120 s limit, no size cap, no progress, PDF only; `downloadDocument` of G1b needs a budget and progress for the agent's jobs.
- **G8 Failure classification:** `error: Download failed` without the reason; needed: `login-required` (401, 403, HTML instead of PDF, login redirect) with the URL, `not-pdf`, the HTTP status; contribute the test of `webFetch.ts`.
- **G9 Security:** S1 (`exec(open …)`) and S6 (`tools-environment.yml` expands secrets) are unchanged and reach more users with the document feature.
- **G10 The warning indicator (stage 2 for the badge, stage 3 for the API):** a `requested` state with a warning badge on the document and on its device or board node, and the resolving action in the context menu; cleared when `path` is set.
- **G11 Easier custom documents:** drag-and-drop of a file onto a device or board node, a default title from the file name, *Add Document* for a URL as well as a file.
