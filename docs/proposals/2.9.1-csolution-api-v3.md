## Problem

This extension reaches CMSIS Solution through hidden commands and API version 2, and rebuilds what the extension knows wherever neither offers it:

- **The target switch rewrites CMSIS Solution's own settings file.** `cmsis_action` with a `target` edits `.vscode/cmsis.json` in the layout of 1.72.0's `CmsisSettingsJsonFile` ([cmsisTarget.ts:17-40](../../src/core/cmsisTarget.ts#L17-L40)), then deactivates and re-activates the solution ([cmsisAction.ts:421-439](../../src/handler/cmsisAction.ts#L421-L439)). Any change of that layout breaks it silently.
- **A failed pack install has no reason.** `cmsis-csolution.installPack` answers the folder or `undefined`; the reason stays in the CMSIS Solution output channel ([installPack.ts:17-32](../../src/handler/installPack.ts#L17-L32)).
- **Nothing is known before the first conversion.** The toolchains, the pack root and the PATH come from `.cmsis/tools-environment.yml`, which exists only after a conversion ([taskProgram.ts:83-100](../../src/handler/taskProgram.ts#L83-L100), [flashTool.ts:144-165](../../src/handler/flashTool.ts#L144-L165)). This is the case of #593: the agent in a fresh window cannot find `cbuild` although the environment is active in VS Code.
- **Missing and used packs are guessed** from `cbuild-idx.yml` and build failures; `cpackget list` in a shell is against the tool rules.
- **Web examples are told apart by a GraphQL query of our own.** `webCatalog.ts` (490 lines) asks Arm's catalogue for the origin pack because API V2 returns web drafts without `pack` (#641).

## Current state

### API V3 on CMSIS Solution `main` (not in the released 1.72.0)

[csolution-api-v3.d.ts](https://github.com/Open-CMSIS-Pack/vscode-cmsis-solution/blob/a9c1e69/api/csolution-api-v3.d.ts), implemented in [v3-api.ts](https://github.com/Open-CMSIS-Pack/vscode-cmsis-solution/blob/a9c1e69/src/api/v3-api.ts); the README calls it "in development". `getApi(3)` extends V2 (`getBoards`, `getDevices`, `getDraftProjects`, `createNewSolution`, `build` unchanged) with:

| Method | Behaviour read from the code | Unavailable |
|---|---|---|
| `getSolutionFile`, `getActiveTarget`, `getDeviceName`, `getBoardName`, `getDfpName`, `getBspName`, `getDfpPath`, `getBspPath`, `getPackRootPath`, `getCbuildRunFile` | delegate to the hidden commands this extension calls today; headless | `undefined`, `''` or `'<not found>'` as the commands answer |
| `activateSolution(path)`, `deactivateSolution()` | the existing commands | reject on failure |
| `getTargets()` | `type[@set]` in declaration order from the loaded csolution | `[]` |
| `setActiveTarget('type[@set]')` | validates the name, writes `.vscode/cmsis.json` under a mutex, copies into the loaded settings, runs `refresh`; "does not wait for conversion to complete" | rejects: no solution, unknown name, save failure |
| `convertSolution({updateRte})` | `csolution convert` of the active target set without the conversion events; `ConvertResult {success, severity, detection, logMessages.errors/warnings/info, toolsOutputMessages}`; `detection` = a compiler or layer choice is required | rejects without a loaded solution |
| `getToolsEnvironment()` | the `tools-environment.yml` text of the window, generated fresh, waits for Arm Tools activation; no solution needed; variable values expanded (S6) | the available environment |
| `getToolchains()` | `{name, version, path, registrationVariable}` from `*_TOOLCHAIN_x_y_z` variables; no PATH scan, no existence check | `[]` |
| `getDebuggers()` | the adapter names of the shipped `debug-adapters.yml`, e.g. `CMSIS-DAP@pyOCD`; not probes, not the configured debugger | rejects when the catalogue fails to load |
| `getPacks({scope, context, filter.text})` | `all` and `installed` from the local index and the RPC; `used` and `missing` need an exact context `<project>+<target>` of the loaded solution; `missing` keeps `pack`, `origin`, `resolvedPack` | rejects: no context, unknown context, every source failed |
| `installPacks({packs, approved})` | sequential `installPack(vendor, name, version)`; `approved !== true` cancels all; one `{pack, status: installed/failed/cancelled, path, error}` per pack | — |

Also on `main`: web drafts carry their origin pack (commit `6e4111c`, #641).

### This extension (2.8.0)

- `acquireSolutionApi` asks for version 2 and checks four methods by name ([solutionApi.ts:164-169](../../src/core/solutionApi.ts#L164-L169)); `cmsis_query` has the kinds `boards`, `devices`, `examples` ([catalogQuery.ts:76](../../src/core/catalogQuery.ts#L76)).
- The getters as commands, feature-detected and fenced at 3 s ([solutionQueries.ts](../../src/utils/solutionQueries.ts), [toolchainPackRoot.ts](../../src/utils/toolchainPackRoot.ts)); the answers interpreted in [solutionAnswers.ts](../../src/core/solutionAnswers.ts).
- `install_pack` with its own licence question from the `.Web/` PDSC ([packInstall.ts](../../src/core/packInstall.ts)).
- `readToolsEnvironment` parses the file ([buildFailure.ts:187-215](../../src/core/buildFailure.ts#L187-L215)); the diagnostic re-run and `flash` take the PATH from it.

## Proposed fix

Every seam keeps today's command or file path as the fallback: a 1.72.0 host sees 2.8.0 behaviour, and the surface changes only where kinds or actions are added. No new tool names: the new abilities are enum values of `cmsis_query` and `cmsis_action`, so `cmsis-help`'s `allowed-tools` and the knowledge base's tool contract stay as they are.

### Phase 1: acquire V3 with fallback (S)

1. `acquireSolutionApi(handle, what, clock, preferred = 3)`: ask for 3, fall back to 2; the `SolutionApiV3` subset typed in `solutionApi.ts`; every V3 method detected by name as the V2 ones are, never by version number (V11). This seam is what 2.9.2's documentation tools call through, including the document methods they will ask CMSIS Solution for.
2. `UPDATE_HINT` names the release that brings V3 once it exists; until then "a release after 1.72.0".
3. The memoised API object per `exports` stays (the catalogue of a window keeps loading across calls).

### Phase 2: getters and the target switch (M)

1. The getters of `solutionQueries.ts` and `toolchainPackRoot.ts` take the API when it is there, the commands otherwise; `solutionAnswers.ts` interprets both.
2. `cmsis_action` with a `target`: `getTargets()` for the choices, `setActiveTarget()` for the switch; the `cmsis.json` editing and the deactivate/activate pair stay as the fallback and are deleted in the release after. The call still waits for the conversion itself (V4), as it does today through the job tracker.
3. `open_solution` through `activateSolution`/`deactivateSolution`.

### Phase 3: `install_pack` through `installPacks` (S)

1. The licence question stays this extension's; `approved: true` is passed only after it. The result's `error` becomes the failure text, `path` the folder; the knowledge line as today.
2. Several packs in one call stay out of the tool shape (one pack per call, as the procedures expect).

### Phase 4: new `cmsis_query` kinds (L)

1. `what: 'packs'` with `scope: all | installed | used | missing`, `context` for the last two, and the existing `name` filter mapped to `filter.text`. `missing` for a context answers what to install before a build, with the `install_pack` call spelled out. The contexts come from `cbuild-idx.yml` as today until V7 gives a getter.
2. `what: 'toolchains'` (`getToolchains`), `what: 'debuggers'` (`getDebuggers`, labelled as the catalogue of adapters, not the probes), `what: 'environment'` (`getToolsEnvironment`, parsed by `readToolsEnvironment`; the `variables` values pass through the secret redaction of `redactSecrets`, and the YAML is never logged). This is #17's `get_toolchain_info` and #41's `toolchain` kind.
3. `flash`, the task program and the diagnostic re-run take the environment from the API when the file is missing. Not "or older than the API's answer": measured on 2026-11-16 ([test/measure/solution-api](../../test/measure/solution-api/README.md)), the API answers in about 1 ms (0.2–0.3 s for the first call of a window), but until the Environment Manager activates the project's vcpkg tools it answers without them, while a file from an earlier conversion lists them; an activation rewrites the file to the API's text. So the file comes first, the API stands in for a missing file, and `activate_environment` drops the API answer cached before it.

### Phase 5: `cmsis_action convert` (M)

1. `convertSolution({updateRte: false})` without a build; the result's `errors` and `warnings` in the reply, `detection` as the hint "choose a compiler or a layer in Manage Solution Settings".
2. The step after a target switch, and the cheap check before `build` when the YAML changed.

### Phase 6: drop the web-catalogue query (S)

When a web draft carries `pack`, `webCatalog.ts` and its `webCatalogFetch` host seam are removed; until then they stay for 1.72.0.

## What changes for the agent and the user

```text
A fresh window, no solution yet

today    cmsis_query {what: 'examples', board: 'B-U585I-IOT02A'} works; "which compiler do I have?" → shell, PATH, guessing
new      cmsis_query {what: 'toolchains'} → AC6 6.24.0, GCC 14.3.1 (registered by Arm Tools); {what: 'environment'} → the PATH entries and CMSIS_PACK_ROOT

Switching the target

today    cmsis_action {action: 'build', target: 'HP@debug'}: edits .vscode/cmsis.json, deactivates, activates, waits
new      the same call; setActiveTarget('HP@debug') does the switch; an unknown name is refused with the declared targets

A build that cannot start

today    cbuild fails, the diagnostic re-run finds "pack not installed"
new      cmsis_query {what: 'packs', scope: 'missing', context: 'App.Debug+HP'} → ARM::CMSIS-RTX@5.9.0 (origin: App.cproject.yml); install_pack for it
```

## Gaps on the CMSIS Solution side

- **V1 No release, no pre-release.** The nightly VSIX (daily, kept one day) is the test baseline; ask for a 1.73.x pre-release so users can run what 2.9.1 is written against.
- **V2 No document methods** (G1b of [2.9.2](2.9.2-documentation-inventory.md), requested as V3 methods with a sketch there).
- **V3 No events:** `onDidChangeActiveTarget`, `onDidConvert`, `onDidChangeSolution`; this extension polls file mtimes.
- **V4 `setActiveTarget` does not wait for the conversion and returns no handle;** `convertSolution` has no cancel.
- **V5 `getToolsEnvironment` is YAML text with expanded secrets (S6);** an object form or a `redacted` option.
- **V6 `getDebuggers` lists the catalogue,** not the configured debugger or the connected probes; `pyocd list` (#81) stays here.
- **V7 No `getContexts()`** although `used` and `missing` need a context name.
- **V8 `installPacks`:** sequential, no progress, licence accepted silently.
- **V9 No `getLayers`** (compatible layers of a reference application, #593).
- **V10 `build()` is V2:** no result or diagnostics through the API.
- **V11 "In development":** shapes may change before the release.

## Decisions for you

- [ ] **1. Fallbacks.** **Recommended:** every V3 use with the 1.72.0 path as the fallback, deleted one release after a CMSIS Solution release ships V3.
  - Alternative: require V3 and refuse on 1.72.0 (`TOOL_DISABLED` with the update hint).
- [ ] **2. The new kinds.** **Recommended:** `packs`, `toolchains`, `debuggers` and `environment` in one release.
  - Alternative: `packs` and `toolchains` first, the other two with #41's remaining kinds.
- [ ] **3. `convert` as an action.** **Recommended:** yes, phase 5.
  - Alternative: only as the step inside the target switch, not exposed.
- [ ] **4. Environment secrets.** **Recommended:** redact variable values with the existing `redactSecrets` rules and say so in the reply.
  - Alternative: answer `environment` only when `redactSecrets` is off.
- [ ] **5. Filing upstream.** **Recommended:** V1, V3, V4, V7 now; V5 and V9 with the security batch.
- [x] **6. Version number.** Decided 2026-11-09: no 2.8.1; the work ships as a 2.9.x preview under the odd-minor rule (2.9.1 as named here), 2.10.0 is the release.

## Tests and acceptance

- **Unit:** `acquireSolutionApi` with exports that offer 3, only 2, neither, or a 3 that lacks a method; the target switch with `setActiveTarget` resolving, rejecting an unknown name, and absent; `installPacks` results `installed`, `failed` with `error`, `cancelled`; each new kind with a scripted API, the `missing` scope with and without a context, the environment with a secret-looking variable redacted.
- **Scenarios:** a fake V3 exports object in `test/transport/config-scenarios.js`; the `dap-scenarios` of `cmsis_action` with a target on both hosts.
- **Surface:** the `cmsis_query` and `cmsis_action` enums and the `cmsis_query` description change; snapshot updated in the same commit; `tools/list` within 33 200 B.
- **Live** with the nightly: a fresh window (`toolchains`, `environment`, `debuggers`, `packs all`); a converted solution (`packs used/missing`, the target switch, `convert`, `install_pack` of a missing pack); the same calls on 1.72.0 (fallbacks).
