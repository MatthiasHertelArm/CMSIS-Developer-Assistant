## Problem

This extension reaches CMSIS Solution through hidden commands and API version 2, and rebuilds what the extension knows wherever neither offers it:

- **The target switch rewrites CMSIS Solution's own settings file.** `cmsis_action` with a `target` edits `.vscode/cmsis.json` in the layout of 1.72.0's `CmsisSettingsJsonFile` ([cmsisTarget.ts:17-40](../../src/core/cmsisTarget.ts#L17-L40)), then deactivates and re-activates the solution ([cmsisAction.ts:421-439](../../src/handler/cmsisAction.ts#L421-L439)). Any change of that layout breaks it silently.
- **A failed pack install has no reason.** `cmsis-csolution.installPack` answers the folder or `undefined`; the reason stays in the CMSIS Solution output channel ([installPack.ts:17-32](../../src/handler/installPack.ts#L17-L32)).
- **Nothing is known before the first conversion.** The toolchains, the pack root and the PATH come from `.cmsis/tools-environment.yml`, which exists only after a conversion ([taskProgram.ts:83-100](../../src/handler/taskProgram.ts#L83-L100), [flashTool.ts:144-165](../../src/handler/flashTool.ts#L144-L165)). This is the case of #593: the agent in a fresh window cannot find `cbuild` although the environment is active in VS Code.
- **Missing and used packs are guessed** from `cbuild-idx.yml` and build failures; `cpackget list` in a shell is against the tool rules.
- **Web examples are told apart by a GraphQL query of our own.** `webCatalog.ts` (490 lines) asks Arm's catalogue for the origin pack because API V2 returns web drafts without `pack` (#641).

## Proposed fix

V3 is required (decision 1, 2026-11-17): every seam this proposal moves to the API loses its command or file path, and on a host without `getApi(3)` the calls that need it answer `TOOL_DISABLED` with the update hint. That covers `cmsis_query` (all kinds, the V2 catalogue ones included, since they come from the same API object), `cmsis_action` with a `target`, `open_solution`, `install_pack` and `convert`. `flash` keeps working on 1.72.0; the documentation and build-artefact tools keep finding the target from the cbuild-run file and the workspace, which are not CMSIS Solution seams. `cmsis_action` without a `target` was to keep working on 1.72.0 as well; since 2026-11-23 it is refused there too, because the getters of the active solution and target are part of V3 and their hidden commands are no longer run (decision 1). The surface changes where kinds or actions are added and in the refusal on old hosts. No new tool names: the new abilities are enum values of `cmsis_query` and `cmsis_action`, so `cmsis-help`'s `allowed-tools` and the knowledge base's tool contract stay as they are.

### Phase 1: acquire V3, refuse without it (S)

1. `acquireSolutionApi(handle, what, clock, preferred = 3)`: ask for 3 only; no answer, or a 3 that lacks a method a call needs, is `TOOL_DISABLED` with `UPDATE_HINT`; the `SolutionApiV3` subset typed in `solutionApi.ts`; every V3 method detected by name, never by version number (V11), so a V3 without a method refuses that call only. This seam is what 2.9.2's documentation tools call through, including the document methods they will ask CMSIS Solution for.
2. `UPDATE_HINT` names the release that brings V3 once it exists; until then "a release after 1.72.0". `get_session_status` says once per session that the CMSIS Solution extension is too old, so the agent learns it before the first refusal.
3. The memoised API object per `exports` stays (the catalogue of a window keeps loading across calls).

### Phase 2: getters and the target switch (M)

1. The getters of `solutionQueries.ts` and `toolchainPackRoot.ts` take the API; the hidden-command calls are deleted, and `solutionAnswers.ts` interprets the API's answers only.
2. `cmsis_action` with a `target`: `getTargets()` for the choices, `setActiveTarget()` for the switch; the `cmsis.json` editing ([cmsisTarget.ts](../../src/core/cmsisTarget.ts)) and the deactivate/activate pair are deleted. The call still waits for the conversion itself (V4), as it does today through the job tracker.
3. `open_solution` through `activateSolution`/`deactivateSolution`.

### Phase 3: `install_pack` through `installPacks` (S)

1. The licence question stays this extension's; `approved: true` is passed only after it. The result's `error` becomes the failure text, `path` the folder; the knowledge line as today.
2. Several packs in one call stay out of the tool shape (one pack per call, as the procedures expect).

### Phase 4: new `cmsis_query` kinds (L)

1. `what: 'packs'` with `scope: all | installed | used | missing`, `context` for the last two, and the existing `name` filter mapped to `filter.text`. `missing` for a context answers what to install before a build, with the `install_pack` call spelled out. The contexts come from `cbuild-idx.yml` as today until V7 gives a getter.
2. `what: 'toolchains'` (`getToolchains`), `what: 'debuggers'` (`getDebuggers`, labelled as the catalogue of adapters, not the probes), `what: 'environment'` (`getToolsEnvironment`, parsed by `readToolsEnvironment`; the `variables` values pass through the secret redaction of `redactSecrets`, and the YAML is never logged). This is #17's `get_toolchain_info` and #41's `toolchain` kind.
3. `flash`, the task program and the diagnostic re-run take the environment from the API when it is there and the file is missing or older than the API's answer; on 1.72.0 they read the file as today, since they are not refused.

### Phase 5: `cmsis_action convert` (M)

1. `convertSolution({updateRte: false})` without a build; the result's `errors` and `warnings` in the reply, `detection` as the hint "choose a compiler or a layer in Manage Solution Settings".
2. The step after a target switch, and the cheap check before `build` when the YAML changed.

### Phase 6: drop the web-catalogue query (S)

Web drafts on a V3 host carry `pack` (#641), so `webCatalog.ts` and its `webCatalogFetch` host seam are removed in this release; `examples` on 1.72.0 is refused with the rest of `cmsis_query`.

## What changes for the agent and the user

```text
A fresh window, no solution yet

today    cmsis_query {what: 'examples', board: 'B-U585I-IOT02A'} works; "which compiler do I have?" → shell, PATH, guessing
new      cmsis_query {what: 'toolchains'} → AC6 6.24.0, GCC 14.3.1 (registered by Arm Tools); {what: 'environment'} → the PATH entries and CMSIS_PACK_ROOT

Switching the target

today    cmsis_action {action: 'build', target: 'HP@debug'}: edits .vscode/cmsis.json, deactivates, activates, waits
new      the same call; setActiveTarget('HP@debug') does the switch; an unknown name is refused with the declared targets

A build that cannot start

today    cbuild fails, the diagnostic re-run finds "pack not installed"
new      cmsis_query {what: 'packs', scope: 'missing', context: 'App.Debug+HP'} → ARM::CMSIS-RTX@5.9.0 (origin: App.cproject.yml); install_pack for it
```

## Gaps on the CMSIS Solution side

- **V1 No release, no pre-release.** The nightly VSIX (daily, kept one day) is the test baseline; ask for a 1.73.x pre-release so users can run what 2.9.1 is written against.
- **V2 No document methods** (G1b of [2.9.2](2.9.2-documentation-inventory.md), requested as V3 methods with a sketch there).
- **V3 No events:** `onDidChangeActiveTarget`, `onDidConvert`, `onDidChangeSolution`; this extension polls file mtimes.
- **V4 `setActiveTarget` does not wait for the conversion and returns no handle;** `convertSolution` has no cancel.
- **V5 `getToolsEnvironment` is YAML text with expanded secrets (S6);** an object form or a `redacted` option.
- **V6 `getDebuggers` lists the catalogue,** not the configured debugger or the connected probes; `pyocd list` (#81) stays here.
- **V7 No `getContexts()`** although `used` and `missing` need a context name.
- **V8 `installPacks`:** sequential, no progress, licence accepted silently.
- **V9 No `getLayers`** (compatible layers of a reference application, #593).
- **V10 `build()` is V2:** no result or diagnostics through the API. PR #720 (open, not merged on 2026-11-18) answers it with `getBuildResult`, the exit code and the terminal output of a build task; its use is [2.9.3](2.9.3-managed-build.md). The draft #713 (a managed build operation) was closed in its favour.
- **V11 "In development":** shapes may change before the release.
- **V12 `getPacks` with `used` or `missing` rejects** "a valid solution must be loaded before proceeding" on a loaded, converted solution whose context is accepted (a wrong one gives "Unknown pack context"); seen on nightly `1.72.1-112` and on the build `1.72.1-104-070dccf` of the since closed PR #713 (2026-11-17). Right after the first load, before `out/` exists, `getBoardName`, `getDeviceName` and `getDfpName` answer `""` while `getSolutionFile` already answers. To file with V1, V3, V4 and V7.

## Decisions for you

- [x] **1. Fallbacks.** Decided 2026-11-17: require V3 and refuse on 1.72.0 (`TOOL_DISABLED` with the update hint); the command and file paths of the moved seams are deleted.
  - Not taken: every V3 use with the 1.72.0 path as the fallback, deleted one release after a CMSIS Solution release ships V3.
  - Confirmed 2026-11-22, with the assumption that a CMSIS Solution release with V3 comes before the next release of this extension. Implemented 2026-11-23, as far as both readings of the open point below share it: only V3 is asked; the target switch through `.vscode/cmsis.json`, the hidden `installPack` command, the activation command of `open_solution` and `webCatalog.ts` are deleted; `get_session_status` has the "too old" line.
  - Decided 2026-11-23, and implemented: the hidden-command getters (`getSolutionFile`, `getActiveTargetSet`, `getCbuildRunFile`, the DFP and BSP folders, the pack root) go too, as phase 2 says. `cmsis_action` is therefore refused on 1.72.0 with the update hint, except `status` and `open_solution` for a folder that is not open yet; the promise that it keeps working there without a `target` is withdrawn.
- [x] **2. The new kinds.** Decided 2026-11-17: `packs`, `toolchains`, `debuggers` and `environment` in one release.
  - Not taken: `packs` and `toolchains` first, the other two with #41's remaining kinds.

  - Not taken: only as the step inside the target switch, not exposed.
- [x] **4. Environment secrets.** Decided 2026-11-17: redact variable values with the existing `redactSecrets` rules and say so in the reply.
  - Not taken: answer `environment` only when `redactSecrets` is off.

## Tests and acceptance

- **Unit:** `acquireSolutionApi` with exports that offer 3, only 2 (refused with the hint), neither, or a 3 that lacks a method (that call refused); the target switch with `setActiveTarget` resolving, rejecting an unknown name, and absent; `installPacks` results `installed`, `failed` with `error`, `cancelled`; each new kind with a scripted API, the `missing` scope with and without a context, the environment with a secret-looking variable redacted.

- **Surface:** the `cmsis_query` and `cmsis_action` enums and the `cmsis_query` description change; snapshot updated in the same commit; `tools/list` within 33 200 B.
