## Problem

An agent that works on a CMSIS solution asks three questions about the source again and again: where is this defined, who uses it, who calls it. Today it answers them with a text search in a shell and by reading files.

- **Text is not symbols.** A search for `osThreadNew` finds comments, the branches of other devices and same-named statics, across the workspace and the pack folder. The device header it then opens can be 2 MB.
- **Some answers a text search cannot give.** The callers of a function over several levels, the classes derived from a type, what a register macro expands to for this device, the size of a struct for the target's ABI.
- **The existing tools answer other questions.** `lookup_symbol` reads the linked image (address, size, section, defining object) and `get_call_stack` a halted target. Neither says where a symbol is written or who refers to it.

clangd answers all of this from an index built with the compile flags of the active context, and Keil Studio already runs it for the editor.

### Measured on 2026-11-22

The probe starts clangd the way the editor's instance is started (only `--compile-commands-dir`), with a copy of a context's compile database in a scratch folder, and speaks LSP over stdio. Apple silicon Mac; the contexts are projects on that machine.

| Context | Compiler | Translation units | clangd | Index complete (cold) | Index shards | clangd memory | Errors clangd reported |
|---|---|---|---|---|---|---|---|
| NXP MCXA156 CAN example | Arm Compiler 6 | 20 | Apple 21.0.0 | 0.4 s | 103 | 363 MB | none |
| ExecuTorch on Corstone-320 | GCC | 36 | Apple 21.0.0 | 0.7 s | 352 | 187 MB | `Unknown argument: '-masm-syntax-unified'` in every file |
| the same | GCC | 36 | ATfE 23.1.0 | 0.7 s | 374 | 204 MB | none |
| ExecuTorch on a Cortex-M33 FVP, C++ | Arm Compiler 6.24.0 | 195 | Apple 21.0.0 | 8.1 s | 1 005 | 1 066 MB | `Unknown argument '-ffp-mode=full'`; `'__config_site' file not found` in armclang's libc++ |
| STM32U585 Blinky with RTX and CubeMX | Arm Compiler 6.24.0 | 62 | Apple 21.0.0 | 0.9 s; 0.09 s with the shards on disk | 144 | 659 MB cold, 150 to 190 MB warm | none in the files opened |

- **M1. Nothing is indexed until a document is open.** `workspace/symbol` answered 0 results in every run before the first `didOpen`; clangd loads the compile database with the first document.
- **M2. The index is fast and stays on disk.** Shards go to `<compile database folder>/.cache/clangd/index/`; a second start with them present was complete in 0.09 s.
- **M3. A request at a position needs the document opened.** Otherwise: `-32602: trying to get AST for non-added document`.
- **M4. By name the index finds functions, variables, types, fields and enumerators**, exact matches first (`main`, `osThreadNew`, `GPIO_TypeDef`, `executorch::runtime::MemoryAllocator`). It does **not** find macros (`HAL_MAX_DELAY`: no result; `GPIOA`: only an unrelated fuzzy match), local variables, or anything in assembler (`Reset_Handler`: no result; clangd logs that it cannot index the startup `.s` file).
- **M5. From a use site everything resolves.** At `main.c:715`, `GPIOA` answers: macro, `#define GPIOA GPIOA_NS`, expands to `((GPIO_TypeDef *)(((0x40000000UL) + 0x02020000UL) + 0x00000UL))`, type and value, defined at `stm32u585xx.h:3110`, 14 references in 7 files. A local variable on the same line answers its definition and its 9 uses.
- **M6. One request gives declaration and definition.** clangd's `textDocument/symbolInfo` returns both ranges; `textDocument/definition` on the name of a definition answers the declaration instead.
- **M7. Answers from the index take 0 to 2 ms**; the first request in a file takes 20 to 400 ms (400 ms in a 2 MB device header).
- **M8. Callers, callees and the type hierarchy work.** `osThreadNew` is called by `app_main` and `app_main_thread` and calls 5 functions; `MemoryAllocator` has the subtype `PlatformMemoryAllocator`. Callers and callees were tried with both clangd builds, the type hierarchy with clangd 21. Callees came with clangd 20 (LLVM 20 release notes: "the outgoing calls direction of call hierarchy"); an older clangd was not tried.
- **M9. Sizes come out for the target.** The hover of a type gives its size and alignment (`MemoryAllocator`: 24 bytes, alignment 4), because the flags name the Cortex-M target.

Not measured on that day, and therefore phase 0: every statement about the editor's client in a real window (requests through the API object, the order of `didOpen` and a request, the location of its shards), a file changed on disk that is not open, Windows and Linux, a multi-project solution.

### Measured in a real window on 2026-11-23 (phase 0)

A throwaway extension in a second VS Code instance (1.147.0, a profile of its own, the installed extensions: CMSIS Solution `1.72.1-115`, vscode-clangd 0.6.0, Arm Environment Manager 1.26.0) opened a copy of this repository's fixture `test/eval/fixtures/corstone-blinky` (GCC, 15 translation units) that had never been converted or built, and asked the editor's clangd through `getApi(1).languageClient`. Nothing of it is committed.

- **P1. The compile database is there without a build.** 4.1 s after the window opened, CMSIS Solution had converted the solution and run `cbuild setup` ("Launching cbuild setup in Terminal to generate IntelliSense database"): the out folder held `compile_commands.json`, `compile_macros_c.h` and the `cbuild.yml`, and no image.
- **P2. The setting carries a variable.** `clangd.arguments` is `--compile-commands-dir=${workspaceFolder}/build/MPS3/GCC/Debug/Blinky/outdir`; the clangd extension substitutes it, and so must whoever reads the setting. The `.clangd` file beside the project has the absolute path.
- **P3. The API works from another extension.** The clangd extension was inactive, activated in 43 ms, and its client ran 100 ms later (Apple clangd 21.0.0). `sendRequest` answered every request of M4 to M8. Reading `exports` of the extension before it is active throws ("is not known or not activated").
- **P4. CMSIS Solution restarts clangd.** Within 4 s of the setup the client object had been replaced. After `clangd.restart` the new client ran in 54 ms, answered a position in a document that was open before at once, and had `main` by name again after 64 ms.
- **P5. M1 holds for the editor's client:** no answer by name before a document is open; 175 ms after the first one, `main` was found, with 105 shards in `<out folder>/.cache/clangd/index`.
- **P6. `openTextDocument` is enough, and in time.** A request sent right after it was answered for a `.c` file and for a header, three of three, without a refusal. A `.h` file is language `cpp` for VS Code.
- **P7. A file changed on disk that is not open is stale until it is opened.** `references` stayed at 3 four seconds after a use was written into an unopened file, was 4 once the file was opened, and 5 after a second write while it was open.
- **P8. The plain commands of VS Code merge providers.** `vscode.executeWorkspaceSymbolProvider('main')` returned 102 symbols, the client 50; the Microsoft C/C++ extension was active beside clangd.
- **P9. A consent comes first.** In a window whose workspace the Arm Environment Manager has not been allowed to activate, it asks with a modal dialog, and until the user answers CMSIS Solution converts nothing: no compile database. The refusal for a missing database names this.
- **P10. A symbolic link in the path costs the file-local symbols.** The first copy lay under `/private/tmp`, for which CMake writes `/tmp` into the compile commands. There clangd did not answer by name for `main` or for static functions unless their file was open, with the editor's clangd and with one started by hand; functions declared in a header were found. Under a path without a link all were found. The search for a use site (decision 6) covers the case.

Not measured still: Windows and Linux, a multi-project solution, `generateClangSetup` off, an environment with the Arm Toolchain for Embedded 23.1, and what `cmsis_action clean` does to the index.

## Can everything be set up automatically?

Almost. Nothing has to be configured by this extension or by the user where Keil Studio already shows IntelliSense for the solution. Two things are not automatic, and a third is a limit.

| Needed | Who provides it | Automatic | When it is missing |
|---|---|---|---|
| The clangd extension | The Keil Studio Pack, and CMSIS Solution's own extension pack | yes | refusal: install or enable it |
| A clangd executable | **Not the pack.** The clangd extension finds one on the window's PATH (the Xcode command line tools; presumably ATfE 23.1 when the solution's vcpkg configuration activates it, not measured) or downloads one when the user confirms its prompt | **no**: one click by the user on a machine without one | refusal with the reason and the command *clangd: Download language server*; the clangd extension shows its own prompt when the call is what activated it (decision 4) |
| The compile database | cbuild, through CMSIS Solution's setup task and every build | yes, when the solution converts and its packs are installed | refusal: `cmsis_action {action:'convert'}` or `build` shows why |
| clangd pointed at it | CMSIS Solution, `generateClangSetup` | yes (default on) | refusal names the setting |
| clangd running with the database loaded | The clangd extension starts with the first C or C++ document, clangd loads the database with it (M1) | **this extension does it**: it activates the clangd extension and opens one translation unit without showing it | |
| The index | clangd, in the background, kept on disk | yes; 0.4 to 8 s the first time (M2) | the answer says how far the index is |
| The right project of a multi-project solution | The user, in the CMSIS view | **no**: clangd serves one project at a time, and there is no API to choose it (gap C1) | the answer names the project it covers |

The limit: the answers are as good as clangd's reading of the compile database. Compiler options clangd does not know (C2), armclang's C++ library (C3) and assembler sources (M4) leave holes that this extension does not repair.

## Proposed design

### Two tools, the third slot unused

`source_find` says what a symbol is and what can be asked about it; `source_get` returns one of those things. A name that is unique may be passed to `source_get` directly, so the common question costs one call.

| Reference tool | Here |
|---|---|
| `workspace_symbol_search` | `source_find {name}` |
| `get_hover` | the card of `source_find`: signature or type, size, doc comment, macro expansion |
| `find_definition` | the card (where it is declared and defined); `source_get {what:'definition'}` returns the text |
| `get_document_symbols` | `source_find {fileFullPath}` |
| `find_references` | `source_get {what:'references'}` |
| `get_call_hierarchy` | `source_get {what:'callers'}` and `{what:'callees'}`, with `depth` |
| `get_type_hierarchy` | `source_get {what:'supertypes'}` and `{what:'subtypes'}` |
| `find_implementations` | `source_get {what:'implementations'}` |
| `get_diagnostics` | not offered as proposed (decision 5, open): `get_build_diagnostics` has the compiler's own messages, and clangd's carry noise of their own here (C2, C3) |

The reference takes a file, a 0-based line and a column for six of its nine tools. An agent rarely has a column, so these tools take a name, or a file and a 1-based line as `add_breakpoint` does.

**`source_find`** takes `name`, `fileFullPath`, `line`, `limit` and `timeoutMs`:

- `name` alone: the index (M4), exact match first, then case-insensitive, then clangd's fuzzy matches. One symbol answers with its card, several with a list of ids. When the index has nothing, the translation units of the context are searched for the word and the first use site is resolved (decision 6), which is how a macro is found by name (M5).
- `fileFullPath`, `line` and `name`: the use site. This is the exact way, and the only one for a local variable.
- `fileFullPath` and `line`: the function or type that contains the line, for a stack frame or a compiler message.
- `fileFullPath` alone: the outline of the file, each entry with its lines.

The card lists the relations that exist for the symbol's kind (a function has callers and callees, a type has supertypes and subtypes, a macro has neither), with counts where they cost a few milliseconds (M7).

**`source_get`** takes `symbol` (an id, or a unique name), `what`, `depth` (1 to 3), `limit`, `maxChars` and `timeoutMs`. `what` is one of `definition`, `references`, `callers`, `callees`, `supertypes`, `subtypes`, `implementations`. Every entry is `file:line` with the source line, so the agent does not open the file to see the use. A hierarchy stops at `limit` entries or at the deadline and says what it left out.

**The id** is `name@path:line:column`, for example `osThreadNew@${CMSIS_PACK_ROOT}/ARM/CMSIS-RTX/5.9.1/Source/rtx_thread.c:2434:14`: readable, and it needs no table on the server, so it survives a reload and a call routed to another window. The handler checks that the name still stands at that place and looks for it nearby when the file has changed. Paths inside the solution folder are relative to it, pack files use `${CMSIS_PACK_ROOT}` as `cbuild-run.yml` does ([cbuildRun.ts](../../src/core/packDocs/cbuildRun.ts) expands it), and the first line of a reply names both folders once.

Both tools are read-only and belong to the pack-docs dispatch like the knowledge ops. `fileFullPath` routes a call to the window that owns the file ([opTable.ts:349](../../src/core/opTable.ts#L349)); a call without one follows the session rules, as the build-artefact tools do. The two definitions get a byte cap of their own, 2 000 B like the knowledge trio; a first draft measured about 2 300 B and has to be cut.

### Where the answers come from

```text
source_find / source_get
   |  dispatch, routed like the build-artefact ops
SourceBrowseHandler            src/sourceBrowseHandler.ts: the VS Code side (extension handle, settings, openTextDocument)
   |
core/sourceBrowse/             no vscode import
   clangdApi.ts                the seam: the clangd extension's API, typed refusals, a client per call
   symbolQuery.ts              name, use site and id to a position; ranking; the search for a use site
   relations.ts                definition text, references, call and type hierarchy within limits
   context.ts                  which context the index covers, how far it is
   render.ts                   cards and lists under the text budget
   |  LSP requests through languageClient.sendRequest, each under a deadline
the editor's clangd            started by vscode-clangd with CMSIS Solution's arguments
```

- **The editor's clangd, not a second one** (decision 1). It is the only instance that is already configured for the active context, its index is already built and in memory, and a second process would cost 150 MB to 1 GB per window. `clangdApi.ts` follows [solutionApi.ts](../../src/core/solutionApi.ts): the extension is optional, activated when installed but inactive, its API detected by shape, every way of not getting a client a typed refusal, and no package becomes a dependency. The wire types are declared here from the LSP specification and clangd's page of protocol extensions.
- **Requests go to the client, not through `vscode.execute…Provider`.** Those commands merge the answers of every provider (on the development Mac cpptools is installed beside clangd, with the conflict warning switched off) and pass vscode-clangd's middleware, which rewrites the names of workspace symbols for a qualified query.
- **One call, in order:** take the client (waiting, with backoff, while it starts); open a translation unit when clangd has no document yet (M1); for a position, open that document through `vscode.workspace.openTextDocument`, so the client sends `didOpen` (M3) and no editor appears; send the requests; read the source lines for the reply from disk. A `-32602` for a document just opened is retried within the deadline.
- **The core is neutral to the transport.** It sees a function `request(method, params, deadline)`. The tests give it a scripted peer; a clangd process of our own (phase 5) would be a second implementation of that one function.
- **Nothing is written.** No `.clangd`, no setting, no download, no index file.

### Replies when something is missing

Each state is its own reply with the existing codes; none is repaired here. Under the rule that a setup another extension owns gets a guided fix, the hints name a knowledge unit, *clangd setup of a csolution*, to be written in `cmsis-knowledge-base` (phase 4).

| State | How it is detected | Reply |
|---|---|---|
| No folder, no solution | as for the build-artefact tools | `NO_WORKSPACE`, `CMSIS_NO_SOLUTION` |
| clangd extension absent or disabled | `getExtension` returns nothing | `TOOL_DISABLED`: part of the Keil Studio Pack; ask the user to install or enable it |
| clangd off, or no executable | the API has no client; `clangd.enable`, `clangd.path` | `TOOL_DISABLED`: which of the two; for a missing executable the command *clangd: Download language server*, which the clangd extension also offers in a prompt when it starts |
| Client starting | its state; CMSIS Solution restarts it after it rewrites the setup | waits inside the deadline, then `TIMEOUT`: repeat the call |
| No compile database | `clangd.arguments` has no `--compile-commands-dir`, or the folder has no `compile_commands.json` | `TOOL_DISABLED`: `generateClangSetup` is off, or the setup failed and `cmsis_action {action:'convert'}` shows why |
| Another context than the active target's | the folder against the out folder of the active context ([artifacts.ts:299](../../src/core/buildInfo/artifacts.ts#L299)) | the answer, with a first line that names the project and context the index covers |
| Index still building | the shards on disk against the translation units of the database | the answer, marked partial: n of m translation units |
| Symbol not found, or several | the lookup | the nearest names; that a macro or a local needs a use site; that an assembler symbol is `lookup_symbol`'s |

### The gate

`cmsis-developer-assistant.sourceBrowsing.enabled`, tagged experimental, read at activation with the reload offer of the other gates, **off** by default: it is experimental, and an experimental feature is off (decision 2). Off, the tools are not in the list and the instructions do not mention them. On, the server instructions gain one sentence that names both tools and tells the agent to use them instead of a search for a symbol across the workspace and the packs. The tool rules of `tool-contract.md`, which users have in their rule files, do not change while the group is experimental.

### Phase 1: the seam and `source_find` (M)

The setting and the gate through [extension.ts](../../src/extension.ts), `DebugMCPServerOptions` and [serverInstructions.ts](../../src/core/serverInstructions.ts); `SOURCE_OPS` in the op table with its exhaustiveness check; the handler in `PackDocsHandlers`; `clangdApi.ts`, `symbolQuery.ts`, `context.ts`, `render.ts`; every refusal of the table above and the line that names the covered context; `source_find` by name, by use site, by line and as an outline. ### Phase 2: `source_get` (M)

`relations.ts`: the definition's text from the extent `textDocument/documentSymbol` gives, references grouped by file, callers and callees with `depth`, the type hierarchy and implementations; the counts on the card; limits, deadline and LSP cancellation; a unique name instead of an id.

### Phase 3: macros by name, and the state of the index (S)

The search for a use site (decision 6), bounded in files, bytes and time; the coverage line from the shards; translation units newer than their shard opened before a cross-file answer, if phase 0 shows that this makes it current.

## Implemented on `release/2.9.5` (2026-11-23)

Phases 1 to 4 as proposed, with these differences and additions:

- **No `timeoutMs` argument.** A call takes milliseconds and the first one of a window under a second; the two definitions are 1 746 bytes together without it. A call ends after 60 s at the latest.
- **`source_find` has no `maxChars`;** its answers are a card, a list of ids or an outline within `limit`. `source_get` has it, 8 000 by default.
- **The waits.** A name is asked again for one second while a new client loads its index, then the use site is looked for, and only while clangd still builds the index (a unit without a shard) is the name waited for up to eight seconds. Waiting eight seconds first made a macro cost seven seconds in a new window.
- **A macro by name** is in the index while an open document includes its header (measured with the real clangd), so the search for a use site is the fallback, not the only way.
- **Only an absolute `fileFullPath` picks a window.** A path relative to the solution folder or under `${CMSIS_PACK_ROOT}` is resolved in the window the session's calls go to. Before, the router appended that such a path "lies outside every open workspace", for every tool.
- **A unit newer than its shard is opened before every call,** at most eight, not only before a cross-file answer (P7).
- **A call that loses its client to a restart is made once more** with the new client (P4).
- **Without `--compile-commands-dir`,** a `compile_commands.json` in the workspace folder or its `build` folder is taken, where clangd finds one by itself, so the tools also answer in a folder that is no csolution.

## Gaps on the CMSIS Solution and clangd side

Reported, not worked around.

- **C1. No API for the clangd context.** Which project the generated setup covers can only be read from the `clangd.arguments` it wrote, or asked with the command `cmsis-csolution.getInfoPath`; choosing one needs the tree item of the CMSIS view. Wanted in API V3: a getter for the compile database folder of the clangd context and a setter by project. Until then this extension reads the setting, which is what the running clangd was started with.
- **C2. Compiler options reach clangd unfiltered.** clangd 21 reports `-masm-syntax-unified` (GCC) and `-ffp-mode=full` (armclang) as errors in every file; clangd 23.1 accepted the first. A `CompileFlags: Remove:` list in the generated `.clangd` would end that.
- **C3. armclang's libc++ does not parse.** `'__config_site' file not found` in a C++ context with Arm Compiler 6.24.0, so symbols that depend on the standard library can be missing.
- **C4. The pack ships no clangd executable.** Only ATfE 23.1 brings one, and only into windows whose solution activates that toolchain.
- **C5. A moved workspace keeps its old `.clangd`.** Many workspaces on the development Mac point to folders that no longer exist. CMSIS Solution rewrites the file when the solution is loaded (read from the bundle); that was not measured.

## Out of scope and follow-ups

- Edits through clangd (rename, code actions, formatting): these tools only read.
- Languages other than C and C++, and assembler sources.
- Repairing the clangd setup, downloading clangd, writing `.clangd`: other extensions own them.
- A row in the tool rules and in the table of replaced shell commands: when the group is on by default.
- A line on the source index in `get_session_status`: the same.
- The reference server is MPL-2.0. Nothing of it is used: no code and no description text. For this proposal its README and three of its source files were read on 2026-11-22 (the tool list, and how it finds and starts clangd); the design shares nothing with them beyond the LSP requests any such tool sends, and takes another route for the transport, the inputs and the tool count. The tools here are written from the LSP specification, clangd's protocol extensions and the clangd extension's API typings; whoever writes them does not open the reference's source. New files carry the Arm Apache-2.0 header, and `npm run provenance:check -- --gate` stays as it is.
