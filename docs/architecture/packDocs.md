# Documentation and build-artefact tools (`packDocs`, `buildInfo`)

Merged from the experimental CMSIS Pack Docs extension. Two pure cores, two
handlers, one dispatch seam, wired into the MCP server and the multi-window
router the same way as the serial tool group. The [knowledge tools](knowledge.md)
share their dispatch and host but have their own handler and are always enabled.

Two working notes under `docs/proposals/` go further than this page: the
[cross-extension call inventory](../proposals/extension-calls.md) lists the
exact calls into other extensions, and the
[document-storage proposal](../proposals/pack-docs-storage.md) separates the
existing storage functions from a proposed provider API, with
[Pack Docs storage at a glance](../proposals/pack-docs-storage-overview.md)
as its one-page map.

## Wiring

- **Op table** (`src/core/opTable.ts`): `PACKDOCS_DOC_OPS` (5) and `PACKDOCS_BUILD_OPS` (5) form `PACKDOCS_OPS`; the shared dispatch also includes `KNOWLEDGE_OPS` (3). `isPackDocsOp`, `isKnowledgeOp` and `isPackDocsDocOp` select the handler. The five documentation ops are `SLOW_OPS` (10-minute router floor). Compile-time coverage checks the op lists against the handlers' `handle*` methods.
- **Every window** builds the documentation, build and knowledge handlers at activation (`extension.ts` → `createPackDocsHandlers`) — they do nothing until called — and hands them to its `ControlServer`, so a forwarded op executes in the window that owns the workspace. The op table selects the serial, documentation, build, knowledge or debugging handler.
- **Downloads** of `fetch_doc` are jobs of the handler, one per document id (`startDownload()` in `src/packDocsHandler.ts`): up to 10 minutes whatever the call waits, so a client that gives up after 60 s no longer ends them. A call waits until shortly before its deadline, then answers `running` with the bytes received (`renderDownloadRunning()`); a later call joins the same download and indexes the PDF once it is in. A failure is kept until a download succeeds: the next call reports it if no reply has, and from the second failed attempt on the reply sends the user to the workspace docs folder instead. `dispose()` aborts what runs (`ResolveContext.signal`); `downloadPdf()` reports progress through `ResolveContext.onProgress`.
- **Router**: `RoutingDebuggingHandler.packDocsOp` forwards like `serialOp`; `WindowCoordinator.sessionHandlers()` returns `packDocs: (op, args) => router.packDocsOp(op, args)`. Documentation and build calls resolve through the pinned / cached / sole-window rungs. Knowledge calls can fall back to the router's window, and `knowledge_search` accepts a `window` argument for its project context; see [windowRouting.md](windowRouting.md#choosing-the-target-window).
- **Gates**: `DebugMCPServerOptions.packDocsEnabled` and `buildInfoEnabled` (default `false` in the options; the settings `packDocs.enabled` and `buildInfo.enabled` are on by default since 2.5.3), fixed per server instance; `registerTools()` registers those two groups only when their gate is on and the session has a dispatch. The MCP `instructions` describe each enabled group and name the setting for a disabled one. Knowledge has no gate: its tools are registered whenever the dispatch exists. The bare single-window `DebugMCPServer` default (tests) has no dispatch and registers none of these three groups.

## The target and its packs

`resolveTarget` (`targetDocs.ts`) asks before it guesses. Explicit arguments
come first. Without a `target`, `cbuildRunFile` or `pack` it takes the
cbuild-run file of the CMSIS Solution extension's active target
(`PackDocsHost.activeCbuildRunFile`, the extension's `getCbuildRunFile`)
when that file exists and names a device-pack; otherwise it scans the
workspace and narrows by `target` and the active context, as before.

A pack is looked for first in the folder the extension names for the active
target's DFP or BSP (`activePackFolders`: `getDfpPath`, `getBspPath`), and
that folder counts only when its PDSC declares the pack (`holdsPack` in
`pdscBooks.ts`). It may lie outside the pack root, which is how a pack a
csolution names with `path:` is found; a relative answer is resolved against
the folders of the target's cbuild.yml files. The resolution carries the
folders as `packDirs`, and `locatePack` takes them before the pack root,
where another installed version stands in for a missing one and the note
says so. The VS Code host asks through `src/utils/solutionQueries.ts`: only
while the extension is active (asking would activate it), through the
getter of CMSIS Solution's API version 3 when it offers one, else the hidden
command, feature-detected, 3 s per answer; `src/core/solutionAnswers.ts`
interprets the answers (`""` and `"<not found>"` are none) for every caller
of the extension's getters.

## CMSIS Solution's document inventory

CMSIS Solution after 1.72.0 keeps a document manager of its own: the CMSIS
view lists the books of the device and board, the Arm catalogue and the
user's additions, and records them in `~/.cmsis/docs.yml`, with downloads
and imports under `~/.cmsis/docs/`. Without a bridge the two managers do
not see each other: what the user adds in the view the agent cannot search,
and a manual the user downloaded there `fetch_doc` downloads again.

`src/core/packDocs/inventory.ts` reads that file as one more source (stage
1 of the 2.9.2 proposal): per call, never written, never watched, parsed
with `js-yaml` and every field checked, since users edit it. An entry is
selected by the resolved device and board; each document becomes a
`DocRef` whose id is derived from `name` the way the pdsc walk and
`fetch_doc` derive it, so no id changes. `mergeInventory` folds them into
`collectTargetDocs`: the same file, URL or Arm id gains `DocRef.inventory`
(CMSIS Solution's local copy, the reason of a failed download, the user
mark); a document only the inventory lists is added, except a pack file,
because the inventory keeps the books of every pack version it ever
converted. The Arm commons only lend their copies: which Arm documents
belong to a target stays `armDocsFor`'s rule, since CMSIS Solution's
selection lacks the ADI, CoreSight and NPU documents.

`PageStore.annotate` reads a web document from CMSIS Solution's copy when
this extension has not downloaded it, so `fetch_doc` indexes it without a
download. A copy under `~/.cmsis/docs/` has its sidecars next to it,
whoever keeps it (CMSIS Solution, the document service, for the user or for
a project): `PageStore.paths` extracts in place, so replacing or removing
the copy (also *Remove Document* in the CMSIS view, which deletes the
copy's folder) takes its index along. A document whose file lies elsewhere
(a pack's PDF, a file of a project) has its sidecars in the folder CMSIS
Solution names for it there, see [Storage](#storage). The handler registers
the service's folders (`PageStore.addRoot`) for the panel's listing and
clear actions: the folder of each copy a target lists and, with the
emulator, the copy store that holds them all. Registered folders can
therefore lie inside one another, or be a link to another; the store walks
each file once (`PageStore.allFiles`), so a document is listed, counted and
cleared once. The listing and `fetch_doc`'s failure name the view's actions
(*Download Document*, *Import Document*). The host sets `PackDocsHost.inventoryFile`;
the tests leave it unset unless they test the inventory.

Stage 2, `inventoryWriter.ts`, behind the setting `packDocs.inventoryRequests`
(off): when a download job of `fetch_doc` ends in failure for a document the
inventory lists, the reason and the user's action go into that entry's
`error`, the field the CMSIS view shows as its error badge; when a later
download of this extension succeeds, it clears what it wrote, and only
that. Ownership is the text's prefix `Requested by the agent:`, so a new
window clears what an earlier one wrote and never CMSIS Solution's own
errors; the listing shows such an error as a pending request. The Arm
commons are never written. Only `error` is written: whether CMSIS Solution keeps a key it does
not know on its next save is not confirmed. The file is CMSIS Solution's
and the user's, so the edit is minimal and checked: the entry is found by
the parsed values of its parent key and `name`, the edited text must parse
to the old data with that one field changed, the file is compared again
right before a temporary file is renamed over it. The view redraws on its
next own write (no watcher yet, gap G1a). With the emulator the document
service writes the same line into `error` itself (below), whatever the
setting says, so the setting adds nothing there.

### The document service (`src/docService/`)

The logistics of a target's documents — which documents belong to a device,
a board, a core, a pack, a vendor, every target or one project; where their
copies are; downloads, imports, removal; the agent's requests — are a
service with a contract of its own, `src/docService/contract.ts`. It is what
this extension asks CMSIS Solution to provide (gaps G1a, G1b, G2, G3, G5,
G7, G8, G10). Until CMSIS Solution does, `src/docService/emulator.ts`
provides it inside this extension. Indexing, search and citations are never
part of it: they stay in this extension.

- **Isolation.** The emulator imports only Node built-ins, `js-yaml` and the
  contract (`src/test/docService.test.ts` enforces it), so it can be handed
  to the CMSIS Solution team as it is. The same test file holds a
  conformance suite of the contract; CMSIS Solution's implementation is to
  pass the same suite.
- **Choice.** `packDocs.documentService` (`auto`): CMSIS Solution's service
  when its API offers `getDocumentService()` with this contract's major
  version (a method name alone is no proof), else the emulator. It is the
  only path: `fetch_doc` downloads nowhere else. `documentServiceOf` in
  `src/packDocsHost.ts`.
- **The retired path.** This extension's own download trees (`arm/`, `web/`)
  and the user documents folder (`~/.cmsis-pack-docs/user`) are retired.
  `legacyMigration.ts` moves the downloads on a window's first resolution
  with a service: they become documents for all targets with their
  edition, then their old copies go. It keeps no record of itself: once
  the old store holds no download it finds nothing, and a document it
  could not move is tried again by the next window. The old records of
  HTML-only documents and the marker file of earlier builds are deleted. The
  user documents folder is neither read nor moved: its sub-folder scheme
  has attributions the service cannot hold (a pattern such as
  `devices/STM32U5*`), and a silent copy would leave two places to look
  after. When it still holds PDFs, activation says once that it is no
  longer used (`tellAboutLegacyUserDocs` in `src/packDocsHost.ts`, the text
  in `userDocs.ts`), so that the user adds what is still needed to a target
  and deletes the rest.
- **Storage: `~/.cmsis/`, shared with CMSIS Solution.** The emulator keeps
  no store of its own: its root is the folder of CMSIS Solution's document
  manager, so the user, the CMSIS view and the agent have one inventory and
  one folder of copies, with or without CMSIS Solution installed. What that
  folder has a place for goes there, in CMSIS Solution's form; the rest goes
  beside it:
  - `docs.yml`, in CMSIS Solution's layout. The emulator writes only the
    fields CMSIS Solution knows (`name`, `title`, `category`, `path`,
    `mode: user`, and `error` as one line while the agent's request is
    open, which the CMSIS view shows as its badge) and keeps everything
    else as read (every scalar as text). A document it adds is a user
    document, because CMSIS Solution drops every other entry of a device or
    board when it renews them for a new pack version; a pack's book it
    fetches keeps its entry. For G2 it adds the lists `cores`, `packs` and
    `vendors`, and the common `all` for documents of every target; an Arm
    document lies in CMSIS Solution's common `arm-docs`. The CMSIS view
    does not show those lists until G2.
  - `docs.xtra.yml`, the emulator's own: what `docs.yml` has no field for
    (the facts of a copy, the typed failure, the request, this machine's
    state of project entries). `error` and `version` mean something else in
    `docs.yml`, and CMSIS Solution rewrites an Arm entry's fields at every
    start, so this state cannot live there. It also outlives the renewal of
    a device's entries and gives a copy back its `path`.
  - `docs/`, the copies, where CMSIS Solution puts them:
    `<Vendor>/<Name>/<document>/<file>` for a device or board,
    `<id>-<version>/<id>-<version>.pdf` for an Arm document; `cores/`,
    `packs/`, `vendors/`, `all/` and `projects/` for what it has no place
    for. A second document of the same name gets a folder of its own.
  - Which documents are the service's: of `docs.yml`, those the user added,
    those with state, and those with a copy under `docs/`. A pack's book
    nobody fetched, and a pack's own PDF, stay CMSIS Solution's and reach
    the tools through `inventory.ts` as before.
  - Writers. Several windows share the folder: a lock file, a fresh read and
    a temporary file renamed over the old one per change, and a watcher for
    changes by other windows and by CMSIS Solution (G1a). CMSIS Solution
    takes no lock: a change is applied once more when `docs.yml` changed
    between the read and the write or right after it; what remains of that
    race is accepted. A write drops comments in `docs.yml` and may change
    its quoting; CMSIS Solution rewrites the whole file on its saves too.
    The watcher also waits for a folder that is not there yet (a project's
    `.cmsis/` before its first document) through its parent, and announces
    a folder that goes.
  - Copies. An import copies the file it is given and never moves or
    deletes it, wherever it lies: the service's own copy picked again, or a
    file below the copy's folder, reached through a link or in another
    spelling of the path, keeps the folder as it is (`copyInto` compares the
    places as the file system spells them).
  Downloads go through `documentEngine.ts`: this extension's resolvers and
  guarded downloader, failures classified (G8). A download runs outside the
  lock, so a long one blocks no other window, and into a partial file of
  its own attempt (`downloadPdf`): two windows that fetch the same document
  each write their own file, and the one renamed last is the copy.
- **Project documents** (G3) are entries in `<csolution folder>/.cmsis/docs.yml`,
  in the layout of CMSIS Solution's `~/.cmsis/docs.yml` (`devices`, `boards`,
  and `cores`, `packs`, `vendors`, `all`): paths relative to the csolution
  folder, or URLs, with title and category. Only what can be shared goes
  there; copies, errors and requests of project entries stay in the user's
  folder (`docs.xtra.yml`, `docs/projects/`). A path that leaves the project
  is not read; a file of another layout is never written. The file is
  changed in place, read with every scalar as text like the user's: what
  the service does not know stays (`commons`, an item's `pack`, lists and
  keys of others), an item that carries more than its key stays when its
  last document goes, and only the comments are lost. Adding is for the
  user by default; the project scope is an explicit choice, and so is its
  removal: `removeDocument` with the csolution takes the project's entry
  and this machine's copy and state of it, never an entry the user has
  under the same name.
- **Parents** match as CMSIS Solution keys them: a device or board without
  a vendor on one side matches by name, a board without a revision likewise
  (`sameParent`). `addDocument` is an upsert.
- **Requests** are recorded only for failures the user can resolve (login
  wall, not a PDF, HTTP, network); a cancel, a limit, a blocked host or an
  HTML-only document is not one. That a document is published as HTML
  only is the service's to keep too: its download fails with the kind
  `html`, which the entry keeps as its `error` (in `docs.xtra.yml` with the
  emulator) until a copy exists; `fetch_doc` adds the edition arm.com gave
  (`resolveDocument` in `webFetch.ts`), and `serviceDocRef` turns the
  failure into `format: 'html'` for the listing. An Arm document outside
  the target's catalogue is listed while that failure stands.
- **The consumer.** `PackDocsHandler.resolve` asks the service for the
  target's parents (`serviceDocs.targetParents`: device, board, cores,
  packs, vendors, all) and `collectTargetDocs` merges the answers
  (`mergeServiceDocs`, ids as before). Several entries can name one
  document (the user's and the project's entry of a URL, one on the device
  and one on all targets): the first counts, most specific parent first and
  the user's before the project's, unless only a later one has the copy, so
  a reference never hides a copy. Two local documents of one parent with
  the same file name are both listed, the second under the id with a hash
  of its own name. `fetch_doc` downloads through the
  service (`fetchVia`) inside the same job, so progress, the wait, the
  failure count and the reply stay as they were; a failure becomes the
  service's request. CMSIS Solution's inventory (`~/.cmsis/docs.yml`), the
  packs and the workspace folders stay read-only sources.
- **The view.** `src/targetDocsView.ts`, *Target Documents* in the Explorer:
  the target's documents by group with their states, a warning and a badge
  for what the agent asked for (G10), and Download, Import a File, Open the
  Vendor Page, Remove and Add Document (G11: file or URL, any parent, for the
  user or the project). *Import Document for Current Target* runs the same
  Add flow. The view shows in a workspace with a csolution, in either
  spelling CMSIS Solution lists (`followSolutions`: searched at activation
  and again when such a file is created or deleted or a folder comes or
  goes). It reads the target's documents while it is shown: when it becomes
  visible, on the service's change event, after its own commands, and when
  a task of CMSIS Solution's build type ends (`mayChangeTarget`), which is
  the only sign of a target switch CMSIS Solution gives: it runs `cbuild
  setup` after one.

The proposed-API path written against the first sketch (stage 3) and its
setting are gone: the contract replaced them.


## Extraction and ranking

- **Extractor** (`pdfExtract.ts`): `PdfjsExtractor` is the bundled default (`packDocs.extractor: auto`/`pdfjs`) — pdf.js legacy build, loaded on first use with a dynamic import; lines are rebuilt from text items by baseline and wide gaps become double spaces so table columns survive. The library runs on a `worker_threads` worker of its own (`pdfWorker.ts`, bundled by esbuild as `dist/pdfWorker.js` beside `extension.js`): pdf.js refuses to start when `Array.prototype` or `Object.prototype` has an enumerable property, and the extension host is shared with extensions that patch them (the CMSIS csolution extension assigns `Array.prototype.groupedBy`) — a worker thread is a fresh realm. `PdfjsExtractor` posts a file path and gets the page texts back; the thread is kept for the next document, retired after a minute idle, and terminated when an extraction times out. Inside the thread pdf.js does not detect Node (Electron), so `GlobalWorkerOptions.workerSrc` points at the shipped `node_modules/pdfjs-dist/legacy/build/pdf.worker.min.mjs` (re-included by `.vscodeignore`), imported there as a fake worker. `itemsToPageText` lives in `pdfText.ts`, shared by the worker and the tests. `PdftotextExtractor` (poppler) stays selectable; a document extracted by the other extractor is re-extracted on its next use so text sources never mix.
- **Tokenizer** (`tokenizer.ts`): NFKC before tokenising, identifier expansion (`RCC_AHB2ENR1` → `rcc`, `ahb2enr1`), hex spellings folded.
- **Index** (`bm25Index.ts`, version 2): body postings plus heading postings per page; BM25 over the body plus `headingWeight` (5) × the heading term score; a version-1 index on disk is rebuilt from `pages.jsonl` on first load. `search.ts` adds phrase, manual and table-of-contents adjustments and a 1.5 heading tie-breaker.
- **Query expansion** (`queryExpansion.ts`): identifier-only queries are expanded from the device SVD at half weight — a peripheral instance with its type synonyms and description, a bare field name with its register and description. Register names, prose and quoted phrases are not expanded (measured: it only dilutes). Expansions never gate the all-terms boost.
- **Benchmark** (`scripts/search-benchmark.ts`, `npm run bench:search`): gold pages are the manual headings that name a register, queries come from the SVD descriptions; reports R@1 / R@3 / MRR per heading weight and post boost, and can extract a PDF with either extractor first. Numbers in `docs/improvement-notes.md` §11.

## Storage

The index of a document is three sidecars (`PageStore`): `<file name>.pages.jsonl`
(the extracted text), `.meta.json` (the file it was made from, its size,
time and hash) and `.idx.json` (the BM25 index). They live where the
documents live, in CMSIS Solution's document folder `~/.cmsis/docs/`
(`PackDocsHost.indexDir`, the store's index root), so that the user, the
CMSIS view and the agent have one folder for a document and what was made
of it. PDFs themselves stay where they are; nothing is written into a pack
or a project.

- **Beside the copy**, for a document that has one in that folder.
- **In the folder CMSIS Solution names for the document**, for a file that
  lies elsewhere. CMSIS Solution derives one folder per document of a device
  or board, the `indexDir` of its `IDocRef`: `<Vendor>/<Name>/<file name
  without extension>`, for a pack's file and a local file as for a URL.
  `indexDirOf` (`indexDir.ts`) is that rule, so a book of a pack has its
  index where CMSIS Solution would put a copy of it. The hardware is the one
  CMSIS Solution's inventory lists the book under, else the target's device
  or board (`DocRef.listedFor`, set by `collectTargetDocs`). What CMSIS
  Solution has no folder for takes the document service's: `packs/<Vendor>/<Pack>/`
  for a pack's PDF that no book names, `cores/`, `vendors/` and `all/` as
  for the service's copies, and `projects/<hash of the folder>/` for a
  project's own files and the workspace docs folders.
- **Two files of one name** (two installed versions of a pack, two folders
  of one pack) would share a folder, which is named by the file and not by
  its place. The one that comes second while the first is still on disk
  gets `<name>-<hash of its path>`, and a cached index counts only for the
  file its metadata names (`isCurrent`), never for another of the same size
  and time. A book of a family is indexed once per device that is used,
  since the folder is the device's.
- **What the store does in that folder** is narrow, because the folder is
  CMSIS Solution's and the user's: it creates folders, writes and removes
  its three sidecars, and removes a folder that a clear left empty. It
  never removes anything else there, and never sweeps for empty folders.
- **The extension's own store**, `<globalStorageUri>/packdocs/`
  (`PackDocsHost.storageDir`), is where earlier releases kept every index
  that had no copy: `<vendor>/<pack>/<version>/` for pack PDFs,
  `workspace/<hash>/`, `user/<hash>/`, `arm/<id>/` and `web/<host>/<hash>/`.
  Sidecars found there move to the document's place on first use. It
  remains the fallback
  when `~/.cmsis/docs/` cannot be written (checked before, and again when
  the write fails) and the whole store of a host without an index folder
  (the tests). Nothing else is written there: what the retired download
  path left (`arm/`, `web/` with `fetch.json`) is read only to be moved
  into the document service, and stays only where that move failed.
